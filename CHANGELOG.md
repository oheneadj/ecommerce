# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Root `.htaccess` forwarding requests into `public/` for hosts pointing the document root at the project root.

### Fixed — StockMovement.quantity allowed zero
- A zero-quantity movement changes nothing but still writes a meaningless row to the immutable `stock_movements` ledger. Added a form-level `not_in:0` rule (`StockMovementForm`) as a courtesy, and the actual enforcement boundary in `RecordStockMovement` itself (throws `InvalidStockMovementQuantityException`) — the single write path for the ledger, so nothing can insert a zero-quantity row regardless of caller.
- 4 new tests: the Action rejects zero and leaves stock/the ledger untouched, and the form rejects/accepts accordingly.

### Removed — Unmodified Laravel scaffold test
- `tests/Unit/ExampleTest.php` was still the default `test_that_true_is_true()` stub generated by `laravel new` — and was also broken as written (extends bare `PHPUnit\Framework\TestCase` with a `RefreshDatabase` trait that no-ops without Laravel's own `TestCase`). Deleted; carried no coverage value.

### Fixed — SESSION_SECURE_COOKIE had no default
- `config/session.php`'s `secure` key was a bare `env('SESSION_SECURE_COOKIE')` with no default — resolves to `null` (cookie sent over both HTTP and HTTPS) unless a deploy explicitly sets the env var, an easy step to forget. Now defaults to `true` in production (`APP_ENV=production`) and `false` otherwise, while still respecting an explicit override.
- 2 new tests: the default resolves to a non-null value, and the config file's default expression matches (guards the fix itself against a future revert to a bare `env()` call).

### Fixed — Filesystem disks silently swallowed write failures
- All three disks (`local`, `public`, `s3`) had the framework's default `'throw' => false`, meaning a failed invoice/image write returns `false` instead of raising — easy to miss in code that doesn't explicitly check every write's return value. Flipped to `'throw' => true` on all three.
- 1 new test asserting all three disks have `throw` enabled, to catch a future accidental revert.

### Fixed — Address had no ULID
- Unlike every other externally-referenceable model (`Order`, `Payment`, `ProductVariant`, `Review`, etc.), `Address` had no `HasUlid` trait or `ulid` column — its raw bigint `id` would have been exposed the moment a customer-facing route needed to reference an address. Currently latent (no storefront exists yet), but fixed now rather than left as a landmine. Added the migration (backfilling existing rows) and the trait.
- 2 new tests: a ULID is generated on creation, and it's used for route-model binding.

### Added — Missing Policy test coverage
- 8 policies had no direct test coverage at all: `ActivityPolicy`, `AttributePolicy`, `StoreSettingPolicy`, `ShippingMethodPolicy`, `StockReservationPolicy`, `StockMovementPolicy`, `ProductImagePolicy`, and `UserPolicy` (including `sendCommunication`) — only incidentally exercised (if at all) through Livewire-level admin tests. Added `tests/Feature/Policies/` with one test class per policy, asserting every ability against every relevant role directly via `$user->can(...)`.

### Fixed — AddItemToCart/MergeGuestCartIntoUser had a check-then-write race
- Both read whether a `cart_items` row already existed for a `(cart_id, product_variant_id)` pair, then decided whether to increment or insert — two concurrent requests (e.g. a double-click "add to cart") could both read no existing row and both try to insert, with the second hitting the table's unique constraint as a raw, unhandled `QueryException` instead of correctly incrementing the first's row. Fixed the same way `CreateOrderFromCart` already locks its cart row: both Actions now lock the relevant cart row(s) with `lockForUpdate()` inside a transaction before the check, serializing concurrent attempts against the same cart.
- No new tests added — the existing "adding the same variant twice" / merge tests already prove the sequential-correctness behavior, and this is a single in-memory SQLite connection in tests, so true concurrent-transaction races aren't independently reproducible here (same limitation as the existing cart-lock in `CreateOrderFromCart`).

### Fixed — Bulk price adjustment bypassed the Action layer and had no transaction
- `VariantsRelationManager`'s `bulkAdjustPrice` computed the new price and called `$record->update()` directly inside the bulk action's closure, unlike its `bulkAdjustStock` sibling (and every other mutation in this codebase) which goes through an Action — and looped over the selected records with no transaction, so a failure partway through a multi-select batch would leave some variants updated and others not. Extracted `App\Actions\Catalog\AdjustVariantPrice` (single-variant percentage adjustment) and wrapped the bulk loop in `DB::transaction()`, matching `AdjustStockWithReservationCheck`'s pattern.
- 4 new tests: the Action's increase/decrease/floor-at-zero behavior, and that an exception partway through a batch rolls back every record in it.

### Fixed — Bug hunt: the notification SMS channel bypassed the audit trail just added
- `SmsChannel` (the "sms" notification channel every `OrderPlaced`/`OrderShipped`/`PaymentSucceeded`/`PaymentFailed`/etc. notification uses) calls the SMS gateway directly — almost certainly higher volume than OTP + ad-hoc customer messages combined, and the one call site missed when `sms_api_logs` was added earlier in this same bug-hunt pass. Now logs every send the same way.
- 1 new test.

### Fixed — Bug hunt: webhook controller's "always 200" guarantee wasn't enforced, order number didn't reset yearly
- `WebhookController`'s docblock promises it always responds 200 so a provider never retries a request already recorded — but nothing caught an exception thrown before `HandlePaymentWebhook` even reaches its own idempotency logic. `PaymentManager::driver()` throws for any unrecognized `{provider}` (a typo'd webhook URL, a bot probing the path), which propagated straight out as an uncaught 500. Wrapped the call in try/catch, logging and still returning 200.
- `OrderObserver` generates `ORD-{year}-{sequence}`, but the sequence was `Order::query()->count() + 1` — an all-time count, not scoped to the year in the number. The year component never actually reset the sequence (Jan 1 of a new year would continue from the prior year's total instead of `000001`), and it was a full-table `COUNT(*)` on every order. Scoped the count to `whereYear('created_at', $year)`.
- 2 new tests: an unrecognized provider still gets a 200, and the sequence genuinely resets across a year boundary.

### Fixed — Bug hunt: payment webhook endpoint had no rate limiting
- CLAUDE.md §12 requires rate limiting on all public-facing endpoints. `POST /webhooks/payments/{provider}` is fully public and unauthenticated — signature verification is the only gate, and every request (even one that fails verification) still writes a `WebhookEvent` row before being rejected. Nothing stopped an attacker from flooding it. Added a generous `throttle:120,1` (120/min per IP) — high enough to never interfere with real, bursty webhook delivery, but enough to block basic abuse.
- 1 new test hitting the real HTTP route and asserting a 429 past the limit.

### Added — Bug hunt: SMS gateway calls had no audit trail
- CLAUDE.md §21 requires every outbound third-party API call to be logged in full (request, response, status code) to a dedicated table — applied to payment gateway calls via `payment_api_logs`, but SMS calls to Moolre (OTP delivery via `RequestOtp`, and the newly-queued customer messages) had none at all. If Moolre silently failed or a customer disputed never receiving a code, there was nothing to check.
- Added `sms_api_logs` (`SmsApiLog` model) mirroring `PaymentApiLog`'s role. Since an OTP send's message body embeds the plaintext code, `request_payload`/`response_payload` use Laravel's `encrypted:array` cast — CLAUDE.md §21's explicit rule for a payload containing a sensitive field ("store them encrypted ... rather than omitting them").
- Extended `SmsSendResult` with `rawResponse`/`statusCode` (mirroring `RefundResult`/`PaymentInitiationResult`) so `MoolreSms` can report them; wired logging into both `RequestOtp` and `SendCustomerSms`.
- 3 new tests: an OTP request logs an entry, the stored column is genuinely encrypted (not plaintext), and a customer SMS logs an entry too.

### Fixed — Bug hunt: customer email/SMS sends blocked the request, no per-item error isolation in bulk
- `SendEmailToCustomer`/`SendSmsToCustomer` called `Mail::to()->send()`/`SmsGateway::send()` directly — synchronous SMTP/gateway calls, violating this project's "external API calls must be queued" convention (already applied to every payment-gateway call and every Notification). Worse in the bulk actions on `CustomersTable`: selecting N customers made N sequential blocking calls inside one HTTP request, with no per-item error isolation — one failure aborted the whole batch with no way to tell which customers had already been messaged.
- Added `App\Jobs\SendCustomerEmail`/`SendCustomerSms` (ShouldQueue, `notifications` queue, with `tries`/`backoff`/`failed()`, matching `GenerateOrderInvoicePdf`'s pattern). The Actions now validate the customer has an email/phone on file synchronously (so the admin still gets immediate feedback), then dispatch the job — a bulk send now returns instantly and each customer's delivery succeeds/fails independently.
- Also added a 10s timeout to `MoolreSms`'s `Http::post()` call, which had none.
- 3 new tests: single-send and bulk-send both dispatch the queued job rather than sending inline.

### Fixed — Image uploads had no size limit
- `->image()` already restricts every upload to image MIME types internally (Filament's `FileUpload::image()` calls `acceptedFileTypes(['image/*'])`), but nothing capped upload size across the 4 image fields (Brand logo, Attribute image swatch, Product image, Variant image) — an admin could upload an arbitrarily large file. Added `->maxSize(config('media.max_upload_size_kb'))` to all 4, backed by a new `config/media.php` / `MEDIA_MAX_UPLOAD_SIZE_KB` env var (default `5120`, i.e. 5MB) so the limit can be changed without a code deploy.
- Also closed a gap found in the same pass: the Attribute Image-type swatch upload (`TermsRelationManager`) was the one image field never routed through `ConvertImageToWebp`, unlike the other 3 — now converts to WebP on save like the rest of the catalog's images.
- 4 new tests: a maxSize rejection test per field group (Brand, Attribute swatch, Product image), plus a WebP-conversion test for the Attribute swatch upload.

### Fixed — Coupon numeric fields had no bounds
- `usage_limit`/`usage_limit_per_user` had no `minValue()` — a `0` would make `usages_count >= usage_limit` true immediately, silently disabling that coupon with no error anywhere. Added `->minValue(1)` (use the existing `active` toggle to disable a coupon, not `0`) and `->minValue(0)` on `min_order_amount`.
- Also fixed a related gap found while in the same form: `value` had no bounds either — a negative value would increase the order total instead of discounting it, and a Percentage value over 100 would discount more than the order is worth. Added `->minValue(0)` and, for Percentage specifically, `->maxValue(100)`. `ApplyCouponToOrder::calculateDiscount()` now also clamps the computed discount to `[0, subtotal]` for both Fixed and Percentage as the actual server-side enforcement boundary — the form validation is a courtesy, not the guarantee.
- 8 new tests: form-level rejection of negative/over-100 values and negative usage limits, and `ApplyCouponToOrder` clamping an over-large Fixed or Percentage discount down to the order's subtotal.

### Fixed — reviews.order_item_id had no explicit delete behavior
- The column was already nullable (freed on review delete/resubmit, fixed earlier this session), but its FK still had no `ON DELETE` behavior — deleting an `OrderItem` with a review would have thrown a raw `QueryException` instead of the only behavior that actually makes sense for an already-nullable column: nulling the reference. Added `nullOnDelete()`.
- 1 new test proving the reference actually nulls out rather than blocking the delete.

### Fixed — 12 foreign keys had no explicit delete behavior
- `products.category_id`, `payments.order_id`, `refunds.payment_id`, `shipments.order_id`/`shipping_method_id`, `coupon_usages.coupon_id`/`order_id`, `stock_movements.product_variant_id`, `reviews.product_id`/`user_id`, and `stock_reservations.product_variant_id` had no `ON DELETE` behavior specified — implicitly restrict at the DB level, but as a raw, unhandled `QueryException` the moment it fired rather than a deliberate choice. Made explicit via `restrictOnDelete()`.
- `product_variants.product_id` and `wishlist_items.product_variant_id` are now explicitly `cascadeOnDelete()` — the former matches `product_images.product_id` on the same parent (already cascading, so deleting a product now consistently takes both its images and variants with it instead of failing partway through); the latter removes a wishlist entry that would otherwise point at nothing once its variant is gone.
- `reviews.order_item_id` is deliberately excluded here — it needs `nullOnDelete()`, not restrict, and is handled as its own fix.
- 12 new tests, one per relationship, each directly proving the actual DB-level behavior (a real `QueryException` for restrict, the child row actually gone for cascade) rather than just checking application-level behavior.

### Fixed — RemoveItemFromCart had no ownership check
- Took a bare `CartItem` and deleted it unconditionally — unlike `RemoveFromWishlist` (and its own sibling `AddItemToCart`), which take the owning `User`/`Cart` and scope through it. Not yet exploitable (no HTTP layer exists for cart/wishlist), but the wrong contract to build a future endpoint on top of — a route passing a raw `CartItem` from a route-model-bound ULID would have no way to verify it belongs to the acting session. Changed the signature to `handle(Cart $cart, ProductVariant $variant)`, matching `AddItemToCart` exactly, and scoped the delete through the cart relationship so it's structurally impossible to reach another cart's line.
- 2 new tests: removing a variant the cart doesn't have does nothing, and the action cannot reach another cart's line item.

### Fixed — Deleting a customer account with order history crashed
- `addresses.user_id` cascades on delete, but `orders.address_id` had no delete behavior (defaulting to restrict) — a customer using the existing self-service "delete my account" feature (`DeleteUserForm`), if they'd ever placed an order, would cascade-delete their address straight into a raw, unhandled `QueryException` on the order's FK constraint.
- Fixed with two changes together: `User` is now soft-deletable (a soft delete is an `UPDATE`, never a `DELETE`, so the cascade never fires at all), and `Order` gained an `address_snapshot` column (frozen at checkout by `CreateOrderFromCart`, same rule as `OrderItem.item_snapshot`) with `address_id` changed to nullable + `nullOnDelete()` — so even if an address is ever removed independently in the future, past orders keep displaying correctly from their own frozen snapshot rather than a live relation that might be gone.
- New `App\Actions\Auth\DeleteAccount` mutates `email`/`phone`/`google_id` to `{original}-deleted-{id}` before soft-deleting — the same "free the unique value for reuse" rule already applied to Product/Review this session — so a customer can delete their account and later register a new one with the same email/phone without hitting a unique-constraint error, and without any of the old (now-inaccessible) account's data ever being exposed to or merged with the new one. `DeleteUserForm` now delegates to this Action instead of calling `$user->delete()` directly, since Livewire components shouldn't hold business logic.
- `OrderInfolist`'s shipping-details display now reads from `address_snapshot` instead of the live `address` relation.
- 10 new/updated tests: the exact crash scenario (order + address + account deletion, no exception), email/phone/google_id mutation and reuse after deletion, a null-safe deletion with no email/phone set, the `nullOnDelete()` path when an address is deleted directly, and the admin order view rendering correctly from the snapshot.

### Fixed — ProcessRefund did not reject a zero/negative refund amount
- The refund cap check (`$amount > remaining balance`) only guarded against amounts that were too *large* — a zero or negative amount passed it trivially, would have been queued to the real payment gateway via `IssueProviderRefund`, and would have driven the proportional-restock math negative. Added a new `InvalidRefundAmountException`, thrown by `ProcessRefund` before the cap check for any `$amount <= 0`. Also added `->minValue(0.01)` to the Filament refund-amount field (via the shared `MoneyInput` helper) so the bad input is rejected with a friendly form error before it ever reaches the Action.
- 4 new tests: zero and negative amounts both rejected at the Action level, confirming no `Refund` row is ever created for a rejected attempt, and the Filament form itself rejecting `0` with a `min` validation error.

### Fixed — Remaining bug-hunt findings (medium/low risk)
- **OTP send could be abused by rotating phone numbers from one source**: the existing per-phone limit (1/60s, 5/hour) resets cleanly for every new number, so an attacker driving unlimited paid SMS sends just needs fresh numbers. Added a 30/hour per-IP limit alongside it in `RequestOtp`.
- **`recovery-codes.blade.php`'s regenerable code list had no `wire:key`** — Livewire's DOM diffing could misalign a code with another's stale `wire:loading` opacity/animation state after "Regenerate codes". Added `wire:key` there and, for consistency, to the (static, lower-risk) appearance-toggle loop.
- **`CreateOrderFromCart`'s duplicate-checkout guard was itself a check-then-write race**: two simultaneous submissions for the same cart could both read "no existing order" and both attempt to create one, with the second hitting a raw unique-constraint `QueryException` on `orders.cart_id` instead of gracefully returning the first result. Fixed by locking the `Cart` row for the duration of the transaction and re-checking inside the lock — same pattern as this project's other contested-resource Actions.
- **Two `catch (Exception)` blocks caught a wider type than intended**: `Security.php` and `RecoveryCodes.php` both guard a `decrypt()` call and should only be catching `Illuminate\Contracts\Encryption\DecryptException`. Narrowed both.
- **`LoginWithGoogle` didn't explicitly check Google's `email_verified` claim** before trusting it as a verified identifier for auto-linking — always true in practice for standard OAuth, but not checked. Now compares against the raw claim (`$googleUser->user['email_verified']`) rather than assuming it; also fixed a real edge case this exposed — if the claim is ever false and the email is already claimed by another account, the new (unlinked) account is now created without that email instead of crashing on the column's unique constraint.
- **`SafeNotifier` logged the raw exception message** on a notification dispatch failure — a theoretical leak vector if an underlying mail/SMS SDK ever embeds sensitive detail in its own exception text. This project's own rule against logging sensitive data explicitly rejects redaction as unreliable, so the message itself is no longer logged at all (only the exception class name); `report()` still routes full detail to whatever error-tracking service is configured.
- **PDF invoice generation ran synchronously** in `SettlePaymentSuccess`/`HandleLatePaymentConfirmation`'s post-commit hook — heavy file I/O with no place blocking the webhook/console process, per this project's "heavy/long-running processing must be queued" convention. Added `App\Jobs\GenerateOrderInvoicePdf` (routed to a `processing` queue) and dispatch it from both call sites instead of calling `GenerateOrderInvoice::run()` directly; the Action itself is still callable synchronously elsewhere (e.g. an admin manually regenerating an invoice).
- 12 new tests covering: OTP phone-rotation abuse and that a different IP is unaffected, the Google unverified-email edge cases (no auto-link, and the unique-constraint-safe fallback), and the invoice job's dispatch + retry/timeout hygiene. The `CreateOrderFromCart` fix relies on existing duplicate-submission coverage — true concurrent-transaction races aren't simulable in this single-process test harness, same limitation as the project's other "concurrent" tests.

### Changed — Payment gateway calls are now queued (bug-hunt: no external API call was ever queued)
- There were zero `Job` classes anywhere in the app — `HandlePaymentWebhook`, `VerifyPendingPayments`, and `ProcessRefund` all called the payment gateway's `verify()`/`refund()` directly in the request/console cycle, with no `$tries`/`$timeout`/`$backoff`/`failed()` safety net, violating this project's own "external API calls must be queued" rule. Worst case: a slow/flaky provider blocked the webhook's HTTP response (risking the provider timing out and retrying) and blocked the admin "Issue refund" action.
- Added `App\Jobs\VerifyPaymentWithGateway` (used by both `HandlePaymentWebhook` and `VerifyPendingPayments` — the exact same re-check-before-and-after-the-call guard that used to live inline now lives once, in the job) and `App\Jobs\IssueProviderRefund` (used by `ProcessRefund`, dispatched only after the refund amount is already locked/reserved synchronously — the fast, contested-resource part stays synchronous; only the slow external call is deferred). Both declare `$tries = 3`, `$timeout = 30`, `$backoff = [10, 30, 60]`, and a `failed()` handler that logs the permanent failure.
- **Behavior change**: `HandlePaymentWebhook` now marks the webhook event `processed_at` immediately after dispatching the verification job, not after the gateway call resolves — receiving and queuing the event is the idempotent action; the queued job's own `payment->status !== Pending` guard is what prevents double-processing. `ProcessRefund` now returns the `Refund` while it's still `Pending` — the Filament "Issue refund" action's success notification changed from "Refund processed" to "Refund queued" accordingly, since the gateway call hasn't necessarily completed by the time the admin sees a response.
- Both new jobs, and all 4 queued Notification classes (`OrderNotification` and its subclasses, `LowStockAlert`, `ReservationsAtRiskAlert`), are now routed to named queues (`external-api`, `notifications`) instead of the undifferentiated `default` — segmentation this project's conventions require but that didn't exist anywhere in the codebase before this change. `docs/infrastructure-deployment.md` updated with the corresponding `queue:work --queue=external-api,notifications` command and a note that payment verification/refunds — not just notifications — now depend on a running queue worker.
- 5 new tests covering: the webhook dispatches (not inline-calls) verification, `VerifyPendingPayments` dispatches one job per pending payment (respecting the existing grace period), `ProcessRefund` dispatches (not inline-calls) the gateway refund and returns a `Pending` result, and both jobs' retry/timeout/queue configuration. Existing payment/refund tests continue to pass unchanged where they exercise the full flow (the test suite's `QUEUE_CONNECTION=sync` runs dispatched jobs inline), with one test updated to check the job's actual DB effect via `->fresh()` rather than the pre-dispatch in-memory object.
- Also fixed a docblock bug found in passing: `Refund.status` was typed `string` in its model docblock despite casting to the `RefundStatus` enum (same class of bug fixed for other models earlier this session) — caught by PHPStan once the new job code compared it against enum cases.

### Fixed — Third bug-hunt round: high-risk findings
- **Review soft-delete didn't free `order_item_id` for reuse**: unlike Product/ProductVariant (already fixed), `Review.order_item_id` is a foreign key, not a string, so the same "mutate to `{value}-deleted-{id}`" trick doesn't apply. `SubmitReview`'s duplicate-check correctly scopes out soft-deleted rows, so a customer deleting their review and trying to write a new one for the same purchase hit a raw unique-constraint `QueryException` instead of working. Fixed by making `order_item_id` nullable and having `DeleteReview` null it out (inside a transaction with the soft delete) — the same "free the unique value" rule, applied via nulling instead of suffixing since it's a FK. The original value remains recoverable via activity log.
- **`ClaimGuestOrder` didn't verify the claiming email was actually verified** — a real account-linking bypass. Changing a profile email nulls `email_verified_at` but doesn't block using the new address elsewhere; `ClaimGuestOrder` matched `guest_email` to the authenticated user's `email` without checking `email_verified_at`, so a logged-in attacker could change their email to a victim's address and immediately claim the victim's guest order (and its order/address history) before ever verifying it. Fixed by requiring `email_verified_at !== null` alongside the existing checks — closing the exact gap this project's own "no auto-link on an unverified identifier" rule exists to prevent.
- **Coupon `value` wasn't required for Fixed/Percentage types**: only hidden for `FreeShipping`, so an admin could save a Fixed/Percentage coupon with a blank value. Checkout would then apply it, consume a usage slot, and silently give a $0/0% discount (`$coupon->value ?? 0` in `ApplyCouponToOrder`) with no error surfaced anywhere. Added `->required()` conditional on the coupon not being `FreeShipping`.
- 6 new tests: Review order-item reuse after delete, guest-order-claim rejection for an unverified email, and Coupon value being required for Fixed/Percentage but not FreeShipping.

### Fixed — Refund race condition and missing authorization (bug hunt, high-risk findings)
- `ProcessRefund` checked the refundable balance (`payment.amount` minus already-refunded) with no row lock, then called the payment gateway and wrote the `Refund` row in a separate, later transaction — two concurrent refund requests for the same payment (an admin double-click, or a manual refund racing `HandleLatePaymentConfirmation`'s auto-refund) could both pass the cap check and both succeed, refunding more than the original payment and over-crediting stock via the paired return movement. Fixed with the same "reserve first, confirm after" shape as `ReserveStockForOrder`: the `Payment` row is now locked (`lockForUpdate()`) inside a transaction that also inserts a `Pending` `Refund` row reserving the amount against the cap *before* the external gateway call ever happens, then a second transaction updates that same row to `Success`/`Failed` once the gateway responds. Pending refunds now count against the cap alongside Success ones, closing the exact window that made the race possible.
- The "Issue refund" table action had no `->authorize()` call at all, despite `PaymentPolicy`'s own docblock explicitly stating refunds are "gated by `update`" — anyone who could merely view the Payments resource could trigger a real refund regardless of what `update()` actually allowed. Added `->authorize(fn (Payment $record) => Auth::user()?->can('update', $record) ?? false)`.
- 4 new tests: a repeated-refunds-respect-the-cumulative-cap test (same shape as this codebase's existing stock/coupon concurrency tests), a Pending-refund-blocks-a-second-refund test proving the reservation itself (not just the eventual Success/Failed status) is what closes the race, and a policy-swap test proving the refund action's authorization actually consults `PaymentPolicy::update()` rather than relying on incidental visibility.
- Found via a 3-way parallel codebase audit (enum-comparison bugs, concurrency/money/snapshot integrity, authorization/N+1) — the remaining findings (soft-deleted Product/ProductVariant not freeing their slug/SKU for reuse, N+1 on 12 relationship columns across 8 admin tables, a few lower-risk authorization gaps, `ShippingMethod` exposing its raw bigint PK) are tracked for follow-up, not yet fixed in this change.

### Fixed — Remaining bug-hunt findings (medium/low risk)
- **Product delete bypassed slug-reuse safety**: `EditProduct`'s header `DeleteAction` and `ProductsTable`'s `DeleteBulkAction` used Filament's plain default delete, calling `$record->delete()` directly and completely bypassing `DeleteProduct` — the Action that mutates a deleted product's slug to `{slug}-deleted-{id}` so it can be reused later. `DeleteProduct` itself was correct and already tested; the admin UI just never actually called it. Both now route through `->using()` to call `DeleteProduct::run()`. (`ProductVariant`'s equivalent delete paths were already fixed earlier this session.)
- **N+1 queries on 8 admin resource tables**: `ActivityLogResource`, `CategoryResource`, `PaymentResource`, `StockMovementResource`, `StockReservationResource`, `ReviewResource`, `OrderResource`, and `ProductResource` all display a relationship column (e.g. `category.name`, `order.order_number`) but none eager-loaded it — every row lazy-loaded its relation individually on every page render. Each now overrides `getEloquentQuery()` with `->with([...])` for exactly the relations its table displays.
- **"Issue refund"-adjacent gaps**: Customer bulk "Send email"/"Send SMS" actions, Orders' bulk "Update status", and Reviews' Approve/Reject actions had no `->authorize()` call at all — reachable by anyone who could merely view the resource, regardless of what a future tightened policy might intend. Added a new `UserPolicy::sendCommunication()` ability for the Customer actions; the others authorize against the existing `viewAny`/`update` abilities (there's no dedicated "moderate" ability, and Review's own `update()` is author-only, so `viewAny` — the actual admin-reach gate — is the correct one to check here, not `update`).
- **`ActivityLogResource` had no backing Policy**: Laravel's policy auto-discovery can't guess a policy for a third-party model outside `App\Models` (`Spatie\Activitylog\Models\Activity`), so it silently found nothing despite `App\Policies\ActivityPolicy` existing in name only. Registered explicitly via `Gate::policy()` in `AppServiceProvider::boot()` — verified via tinker that `Gate::getPolicyFor()` returned `null` before this fix.
- **`ShippingMethod` exposed its raw bigint PK** in admin edit URLs (`/admin/shipping-methods/3/edit`) — unlike every comparable resource. Added a `HasUlid`-backed `ulid` column (new migration, backfilled for any existing rows) matching the convention used by `Order`/`Payment`/`Refund`/`ProductVariant`/`Coupon`.
- 9 new tests: Product delete-routing (single + bulk + slug-reuse-after-delete), the eager-loading assertion (parameterized across all 8 resources), and the `ShippingMethod` route-key regression.

### Added — Global product attribute catalog (step 1 of the variant-attribute rework)
- New `Attribute` (`name`, `slug`, `type`: text/color/image) and `AttributeTerm` (`value`, `slug`, `swatch_value`) models, plus `Attribute::products()` / `Product::attributes()` and `AttributeTerm::productVariants()` / `ProductVariant::attributeTerms()` many-to-many relations — a WooCommerce-style reusable attribute catalog (Size, Color, Material...), defined once and shared across products, instead of every variant retyping the same values as free text. The existing free-typed `AttributeValue` model/table is untouched and remains the "custom/local attribute" escape hatch for one-off values that don't need to be reused.
- `AttributeResource` (Filament, grouped under the same "Catalog" nav section as Products but not scoped to any single product record, since attributes are reused across the whole catalog) — list/create/edit attributes, with a `TermsRelationManager` for managing each attribute's values. ### Added — Sprint 4 (Payment Integration, Epic E5)
- `Payment`, `Refund` models/migrations, plus the two audit-exempt tables from `technical-design-ecommerce.md` §4g: `payment_api_logs` (every outbound call to a provider) and `webhook_events` (every inbound webhook, unique on `(provider, event_id)`). Both are written and committed on their own, before any related business-transaction processing — never nested inside it, so a rollback of order/payment bookkeeping can never erase evidence that a charge was attempted or a webhook arrived.
- `App\Enums\PaymentStatus` and `RefundStatus` backed enums.
- `App\Payments\` — a `PaymentGateway` contract, `PaymentManager` (Laravel Manager pattern, mirrors `App\Sms\SmsManager` exactly), and `MoolreGateway`/`PaystackGateway` drivers, resolved via `config/payments.php`'s channel→provider mapping (`mobile_money` → Moolre, `card` → Paystack) so both providers can be active side by side. Card/payment details are never handled directly by this platform — Paystack's hosted checkout keeps card data entirely out of PCI scope; no driver logs a raw card number.
- Payment Actions (`app/Actions/Payment/`): `InitiatePayment` (idempotent per order — reuses an existing pending payment rather than duplicating), `HandlePaymentWebhook` (verifies the provider's signature before anything else; never trusts the webhook's own reported status, always re-verifies server-side via `PaymentGateway::verify()`; idempotency is layered — the unique `(provider, event_id)` index plus a `processed_at` check, so a retried delivery never double-fulfills), `ProcessRefund` (refund amount capped against the payment's amount minus whatever's already been refunded — cross-row arithmetic the database can't constrain — restores stock via a `return` `StockMovement`), `VerifyPendingPayments` (scheduled every 2 minutes, the polling fallback for a slow/missing webhook), `HandleLatePaymentConfirmation` (a payment confirming after its reservation already expired either fulfills directly if stock is still available, or auto-refunds and cancels the order if not), and `SettlePaymentSuccess` (the shared success-handling logic both the webhook handler and the poller funnel through, so whichever arrives first "wins" and neither double-processes).
- `POST /webhooks/payments/{provider}` — thin controller, all logic in `HandlePaymentWebhook`; exempted from CSRF verification (a payment provider can't obtain a token — the driver's signature check is this endpoint's actual authenticity gate).
- Filament: read-only `PaymentResource` (no create/edit — only `InitiatePayment` creates a payment, only the webhook/polling/late-confirmation Actions change its status) with an "Issue refund" table action calling `ProcessRefund`, and a read-only `RefundsRelationManager`. `PaymentPolicy`/`RefundPolicy` are Admin/Super-Admin-only, same scope as Order/Coupon.
- `PaymentManager` registered as a container singleton in `AppServiceProvider` (mirroring `SmsManager`) — required for `PaymentManager::extend()`-registered test doubles to actually be seen by Actions resolving the manager via constructor injection.
- 14 new feature tests against a `FakePaymentGateway` test double registered via the same public `PaymentManager::extend()` point a real new provider would use — covering initiation idempotency, outbound call logging, webhook signature rejection, duplicate webhook delivery, the mutual idempotency of polling vs. webhook confirmation, both branches of late payment confirmation, and the refund-amount cap (including after a prior partial refund).

### Changed — notifications are now queued
- All six notification classes implement `ShouldQueue` (`QUEUE_CONNECTION=database`, already configured). Matters most for `HandlePaymentWebhook`: it's a synchronous HTTP endpoint the payment provider calls, and blocking on an SMS/email round-trip there risked the provider timing out and retrying the webhook. `SafeNotifier`'s docblock updated to reflect that it now guards dispatch-time failures (the queue push itself); real delivery failures happen later inside the queue worker, governed by the queue's own retry/`failed()` handling. Requires an actual queue worker running in production — noted as the user's responsibility to provision (e.g. via a cron-driven `schedule:run` + supervisor, or a dedicated worker process).

### Changed — Filament navigation polish
- Every resource now has a distinct Heroicon (previously most shared a generic placeholder) and a `navigationGroup`, organizing the sidebar into **Catalog** (Products, Categories, Brands), **Inventory** (Stock Movements, Stock Reservations), **Sales** (Orders, Payments, Coupons, Shipping Methods), **Reviews**, **Reports** (Activity Log), and **Settings** (Store Settings).

### Added — Development seed data
- `database/seeders/{RoleSeeder,UserSeeder,StoreSettingSeeder,ShippingMethodSeeder,CatalogSeeder,CouponSeeder,OrderSeeder}.php`, orchestrated from a rewritten `DatabaseSeeder`.
