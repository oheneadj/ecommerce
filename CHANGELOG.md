## [Unreleased]

### Added — Personalized greeting on the admin dashboard
- The admin Dashboard page's title is now "Welcome, {name}" instead of the generic "Dashboard", falling back to the generic title for the rare case a user has no name set.

### Added — SMS for operational admin alerts
- `LowStockAlert`, `CriticalHealthAlert`, and `ReservationsAtRiskAlert` previously only notified via mail+database. Now that staff accounts have phone numbers on file (the Staff resource requires one), all three also send SMS — genuinely time-sensitive operational alerts, unlike `StaffInvited`'s deliberately link-free SMS, so there's no reason to withhold detail here. `SmsChannel` already no-ops gracefully for a recipient with no phone on file (e.g. the CLI-created Super Admin, which doesn't collect one), so this is a safe unconditional addition to each notification's `via()`.
- 3 new tests confirming the `sms` channel is included alongside `mail`.


### Added — "Staff" admin resource (5/N, completes the invite/management feature)
- Final piece: a new Filament resource (`Settings` nav group) to invite and manage Admin/Store Keeper accounts — the user-facing entry point for everything built in the previous four pieces. Ties together `InviteStaffMember` (create), `SendStaffInviteNotification` (resend), and `SetStaffDisabledState` (disable/enable, single + bulk, both behind a confirmation modal explaining exactly what happens).
- Since `CustomerResource` and this new resource are both backed by `User`, and Filament resolves `viewAny`/`create`/`update` authorization through one Policy per model class rather than per Resource, this resource overrides `canViewAny()`/`canCreate()`/`canEdit()` directly (Super Admin only, per BRD §3) instead of risking `UserPolicy` — reusing it would have wrongly granted Admin access to staff management.
- Super Admin accounts are excluded at the query level (`getEloquentQuery()`), not just hidden from the table — a direct URL to a Super Admin's record 404s here, since every route this resource has (list/create/edit) resolves through the same scoped query.
- 11 new tests (`StaffResourceTest`) covering access control, the Super-Admin-exclusion query scope (including the direct-URL case), invite-on-create, role changes on edit, resend-invite visibility, and disable/enable (single + bulk).


### Added — Disable/enable staff accounts (4/N)
- Fourth piece of the staff invite/management feature. `SetStaffDisabledState` is the single entry point for both directions: disabling immediately deletes the account's rows from the `sessions` table (the `database` session driver) so an active session is kicked out right away, not just blocked on the next login attempt. Re-enabling never restores access under the old password — a fresh unguessable placeholder replaces it and a new set-password invite goes out via `SendStaffInviteNotification` (mail+SMS), which matters most for "disabled over a security concern."
- The disabled/enabled transition is logged to the audit trail (BRD FR-10.2) via `User` gaining the existing `LogsAdminActivity` trait, scoped to just `disabled_at` (not every fillable attribute — a customer editing their own profile isn't "significant administrative action", only a staff account's access state is). Spatie Activitylog attributes the entry to the acting Super Admin automatically from the current auth guard, no manual `activity()->causedBy()` call needed.
- 5 new tests (`SetStaffDisabledStateTest`).

### Added — Staff invite notification and actions (3/N)
- Third piece of the staff invite/management feature. `StaffInvited` — a distinctly-worded invitation, not the generic "forgot password" copy — sent via both mail and SMS (confirmed with the user): mail carries the actual set-password link, SMS is a heads-up only ("you've been invited, check your email") with no link or token in it, since SMS is unencrypted and the phone isn't OTP-verified at invite time.
- `SendStaffInviteNotification` generates a real password-reset token through the same broker Fortify's "forgot password" flow already uses and points it at the existing `password.reset` page — no new routes/pages needed. `InviteStaffMember` creates the account with an unguessable random placeholder password (never null — no edge case in credential checking) and calls it. Both reused later for a "Resend invite" action and for re-enabling a disabled account.
- 4 new tests (`InviteStaffMemberTest`).

### Added — Strong passwords enforced for staff, in every environment (2/N)
- Second piece of the staff invite/management feature. `AppServiceProvider` only required a strong password (12+ chars, mixed case, numbers, symbols, not a known-compromised password) in production — everywhere else, Laravel's bare 8-character minimum applied, including to staff/admin accounts. Extracted the rule into `App\Support\PasswordPolicy::strong()` (a plain class, not a trait — traits can't be called statically without a deprecation warning unless something actually `use`s them, and neither `AppServiceProvider` nor the Fortify action naturally does) and applied it unconditionally in `ResetUserPassword` whenever the account being reset holds any staff role, regardless of environment — customers keep the existing environment-based default.
- `ResetUserPassword` also now stamps `email_verified_at` on a successful reset if not already set — using a mailed token proves inbox ownership, whether it's an ordinary "forgot password" or (in the next piece of this feature) a staff invite/re-enable link.
- 6 new tests (`PasswordResetTest`).


### Added — Foundation for the staff invite/management feature (1/N)
- First piece of a new "invite an admin user" feature (currently only possible via the CLI's `app:create-super-admin`, which is Super-Admin-only and meant for the very first bootstrap account). New nullable `disabled_at` timestamp on `users` — a timestamp rather than a plain boolean so a disabled account carries a visible "since when" on the record itself, same evidence-bearing-state convention `email_verified_at`/`phone_verified_at` already use. `User::canAccessPanel()` now also blocks a disabled account at the panel gate.
- New `User::scopeStaff()` — deliberately scoped to `role IN (admin, store_keeper)`, not a generic "has any role" filter (unlike its `scopeCustomers()` counterpart) — Super Admin must never resolve through it, since the upcoming Staff resource uses this scope to gate every route it has (list/create/edit), not just what's hidden from a table.
- 4 new tests (`UserTest`).

### Added — Duplicate a product from the admin panel
- New "Duplicate" row action on the Products table (`App\Actions\Catalog\DuplicateProduct`), copying the product's own fields (name gets " (Copy)" appended, slug gets a guaranteed-unique suffix using the same row-ID pattern `DeleteProduct` uses to free a slug on delete), its enabled global attributes, every variant (fresh SKU via the same ID-suffix pattern, custom attribute values, and shared global attribute-term links), and every image. The copy always starts as Draft, regardless of the original's status — never accidentally live before review.
- Images are **physically copied to new files on disk**, not just new `ProductImage` rows pointing at the original file — `ProductImageObserver` deletes the underlying file whenever *any* row referencing it is deleted, so sharing a path between two products' image rows would mean deleting either product's image deletes the file out from under the other. Verified with a regression test that deletes the original's image and confirms the copy's file survives.
- Not copied: reviews and stock movements/reservations — real history belonging to the original product, not template data for a copy.
- 9 new tests (`DuplicateProductTest`).

### Fixed — Queued jobs on named queues never ran in local dev
- `composer run dev` (Laravel's built-in `artisan dev`) starts a `queue:listen` process with no `--queue` flag, which only services the `default` queue. This project deliberately segments every job onto a named queue (`emails`/`sms`/`notifications`/`processing`/`external-api`, per CLAUDE.md §15) so time-sensitive work never queues behind slow external-API work — but that segmentation meant the dev queue listener was never actually working any of them. 38 jobs had piled up undelivered, including a just-sent customer broadcast notification, order confirmations, and low-stock alerts going back to when queue segmentation was introduced.
- `AppServiceProvider::configureDevQueueWorker()` re-registers the `queue` dev command (`DevCommands::artisan(...)`) with `--queue=notifications,emails,sms,processing,external-api,default` — a userland registration wins over the framework's default per `DevCommands::resolvePriority()`. Drained the existing backlog manually (`php artisan queue:work --queue=... --stop-when-empty`); 33 succeeded, 5 pre-existing SMS jobs failed on a missing local Moolre API key (a separate, expected local-env gap — not something to paper over with fake credentials).
- Requires restarting any already-running `composer run dev` process to take effect (it's a boot-time provider registration).

### Added — Queued fan-out for customer broadcast notifications
- Second piece of the customer-broadcast-notifications feature: `BroadcastMessageToCustomers` (Action) resolves a recipient query to a plain ID list and dispatches a new queued `FanOutCustomerBroadcast` job (`processing` queue), rather than looping and dispatching per-customer jobs inline during the admin's request — "all customers" could mean thousands of rows. `FanOutCustomerBroadcast` chunks (200 at a time) and, per customer per selected channel, reuses the existing `SendEmailToCustomer`/`SendSmsToCustomer` Actions (email/SMS) or calls a new `CustomerBroadcastNotification` (`database` channel only — email/SMS aren't routed through Laravel's notification channels here, to keep exactly one delivery path per channel). A customer missing the contact method for a selected channel is silently skipped for that channel, same as the existing bulk Customers-table actions.
- The in-app leg (`CustomerBroadcastNotification`) writes to the same `notifications` table as everything else `Notifiable` — it does **not** surface via the Filament admin bell, since customers never log into the admin panel; a storefront-facing notification center is the next piece of this feature.
- 8 new tests (`BroadcastMessageToCustomersTest`).

### Added — Lazy loading + skeletons on Cart and Checkout
- `CartPage` and `CheckoutPage` are now `#[Lazy]` with a matching skeleton placeholder (same pattern already used by `CartIndicator`/`SearchAutosuggest`) — the outer page shell (nav, layout) paints immediately while the cart/checkout queries run, instead of the customer staring at a blank page during the delay. Real heading text (`My Cart`, `Checkout`) stays visible in the placeholder (not greyed out) so the page title and `assertSee`-style checks aren't affected by the swap; only the dynamic content below is skeletonized.
- **Deliberately excluded from this treatment**: `ProductListingPage` (making it lazy would mean real product names/prices are no longer in the first HTML response — a genuine SEO/crawlability regression for the site's most search-indexed page) and `ProductDetailPage` (its `mount()` does `Product::where('slug', ...)->firstOrFail()`, which is what makes an invalid/removed product slug return a real HTTP 404 — deferring `mount()` via `#[Lazy]` would turn that into a 200 + placeholder, with the "not found" only surfacing afterward as an awkward Livewire error instead of a proper 404 page).
- Testing note: `Livewire::test()` on a `#[Lazy]` component renders the placeholder on its very first call, and (for a component whose `mount()` sets real defaults, like `CheckoutPage`) simply calling `->set()`/`->call()` afterward does **not** retroactively run `mount()` — pass `['lazy' => false]` as the test's mount params to disable lazy loading for that test run and get normal, fully-mounted behavior.
- 2 new tests (`LazyLoadingSkeletonsTest`) confirming the first response shows a skeleton, not real content; `CheckoutPageTest` updated to disable lazy loading per the note above.

### Fixed — Price slider snapped/readjusted itself right after dragging
- The previous fix used a separate `click` handler on the track for click-to-jump alongside `mousedown` on each thumb for dragging. A fast drag leaves the thumb's DOM position one Alpine reactivity tick behind the cursor, so on release the browser's synthetic `click` event lands on the track rather than the thumb (`@click.stop` on the thumb never runs) and fires a second, slightly different jump immediately after the drag already committed — visible as the slider "moving by itself" right after letting go. Unified both interactions into a single `mousedown`/`touchstart` handler on the track (nearest thumb is chosen from the pointer's position, whether that's the first pixel of a drag or a plain click) so there's no second code path left to race. Verified with a scripted fast-drag CDP test asserting the value immediately after release matches the value after the follow-up Livewire request settles (no post-release jump).

### Fixed — Price slider didn't render or drag correctly
- The dual-thumb slider shipped as two overlapping native `<input type="range">` elements with `pointer-events` CSS tricks to let each thumb "win" over the other's full-width hit area. That approach was unreliable in practice — the thumb overflowed the 4px-tall track, and there was no click-to-jump on the track since the whole input had `pointer-events: none` outside the thumb itself. Rebuilt as a self-contained Alpine-driven slider (plain `<div>` track/thumbs, `getBoundingClientRect()` + pointer math) with proper click-anywhere-on-track and thumb-drag support. Dragging updates local Alpine state only; the actual `minPrice`/`maxPrice` filter commits via `$wire.set()` once on drag release or track click, not on every pixel of movement, so it doesn't hammer the server mid-drag. Verified visually (screenshots, light and dark) and via a scripted CDP drag/click that confirmed both interactions filter the product grid correctly with no console errors.

### Changed — Price filter on the product listing sidebar is now a dual-thumb slider

### Added — Typo-tolerant autosuggest search in the navbar
- The navbar search box did plain SQL `LIKE` substring matching only — "nke" never found "Nike". New `App\Actions\Catalog\SearchProducts` action adds fuzzy matching: exact/substring matches always rank first, then per-word Levenshtein (edit-distance) scoring catches typos, with a small tolerance scaled to the search term's length. No dedicated search engine (Meilisearch/Typesense/etc.) — explicitly ruled out (shared hosting) — so this works on plain Eloquent against either SQLite (dev) or MySQL (production), scanning a capped batch (300) of active/purchasable products per search. Reused by both the navbar and `/products`' own search box (`ProductListingPage`), so typos are corrected in both places from one implementation, memoized per request via `#[Computed]` so the facet-filter computation (which calls the same base query many times) doesn't re-run the search itself repeatedly.
- New `App\Livewire\Storefront\SearchAutosuggest` — a live search-as-you-type dropdown embedded in the navbar (`#[Lazy]`, matching the existing `CartIndicator` pattern, with a matching placeholder so there's no layout shift), showing up to 8 suggestions with thumbnail + price, a "View all results" link, and a skeleton (`wire:loading`) while a debounced (300ms) search is in flight — so a slow query never leaves a blank dropdown. Replaces the plain `<input>` that used to sit directly in the navbar.
- Rate-limited (60/min per IP, generous relative to real debounced usage) to stop a scripted flood of rapid-fire searches from hammering the database — a rate-limited request just returns no new suggestions rather than erroring.
- 13 new tests (`SearchProductsTest`, `SearchAutosuggestTest`), `NavbarSearchTest` updated for the new lazy-loaded markup.

### Added — Dynamic attribute filters (Color, Size, etc.) on the product listing sidebar
- The listing page had Search/Category/Brand/Price filters but nothing for global attributes. New filter groups appear per attribute, but only when it has at least one term genuinely in use somewhere in the active/in-stock catalog (`ProductListingPage::filterableAttributes()`) — an attribute whose only term was never assigned to any variant gets no group at all.

- Multiple terms within one attribute are OR'd (Red or Blue); multiple attributes are AND'd.
- 5 new tests in `ProductListingPageTest`. Manually confirmed query count stays well within budget (14 queries for a full render with 4 attributes in the dev catalog).
- **Found and fixed along the way**: the field initially used `<x-input>`, whose `@error()` directive depends on Laravel's `$errors` view-share, which is only bound during the normal middleware pipeline — error pages (404/403/500) render outside it but still use this same layout, so every error page crashed with an undefined `$errors` variable. Switched to a plain styled `<input>` (this field is never validated, so it never needed that behavior) — no other page using `<x-input>` is affected, since they're all reached through the normal pipeline.

### Fixed — Checkout no longer orphans an order when payment fails to initiate

### Fixed — Payment initiation no longer throws an uncaught exception on a misconfigured/unreachable provider

### Fixed — Product detail page: selected variant/attribute reverted on reload, and most catalog products had no way to reach a second variant at all
- Root cause 1: the variant switcher only ever looped `$product->attributes` (the product-level Attribute pivot). Most catalog products have variants distinguished purely by SKU/price with no global Attribute attached, so that loop rendered nothing — the customer could only ever see `variants->first()`, with every other variant permanently unreachable even though the data was fine. Added a fallback "Options" list (`ProductDetailPage::hasAttributeSelector`/`selectVariant()`, new `ProductVariant::display_label` accessor) whenever a product has multiple variants but no Attribute selector to show.
- Root cause 2: whichever variant/attribute-term the customer picked lived only in Livewire component state — a reload always reverted to the default. Added `#[Url]` to `$selectedVariantId`/`$selectedTermIds` so the choice round-trips through the URL (`?variant=id` / `?options[attributeId]=termId`) and survives a reload or a shared link.
- Found and fixed a second bug while adding the above: values restored from the URL come back as strings, but the attribute-term matching logic compared them with strict `===` against integer IDs — silently failing and falling back to the default variant. Added explicit `(int)` casts on both sides of that comparison.
- Regression tests in `ProductDetailPageTest` for both the fallback list and URL round-tripping — the URL-persistence test for attribute terms is what actually caught the string/int comparison bug.

### Fixed — Checkout form showed the wrong validation error under nearly every field
- Root cause: the shared `<x-input>` component (`resources/views/components/input.blade.php`) displayed errors via `@error($attributes->get('name'))`, but no caller anywhere passes a `name` HTML attribute — every usage binds through `wire:model`/`wire:model.live`/etc. instead. `$attributes->get('name')` was therefore always `null`, and Laravel's `MessageBag::has(null)`/`first(null)` are defined as "has any error at all" / "the first message in the whole bag" — so every `<x-input>` on the page, including ones never actually validated (the optional "Address line 2" and "Region" fields) and entirely unrelated ones (the Order Summary's coupon code field), rendered the very first error registered anywhere on the page.

- Removed the now-redundant hand-rolled `@error('guestX')` blocks in `checkout-page.blade.php` — each `<x-input>` was duplicating the same message once its own scoping was fixed.
- New regression test in `CheckoutPageTest` asserting the guest-name error appears exactly once rather than bleeding into every other field — verified meaningful by reverting the fix and confirming the count jumps to 9.

### Fixed — Bug hunt: webhook controller's "always 200" guarantee wasn't enforced, order number didn't reset yearly

### Fixed — Bug hunt: payment webhook endpoint had no rate limiting

### Fixed — Deleting a customer account with order history crashed

### Fixed — ProcessRefund did not reject a zero/negative refund amount

### Fixed — Remaining bug-hunt findings (medium/low risk)
- **OTP send could be abused by rotating phone numbers from one source**: the existing per-phone limit (1/60s, 5/hour) resets cleanly for every new number, so an attacker driving unlimited paid SMS sends just needs fresh numbers. Added a 30/hour per-IP limit alongside it in `RequestOtp`.
- **`recovery-codes.blade.php`'s regenerable code list had no `wire:key`** — Livewire's DOM diffing could misalign a code with another's stale `wire:loading` opacity/animation state after "Regenerate codes". Added `wire:key` there and, for consistency, to the (static, lower-risk) appearance-toggle loop.
- **`CreateOrderFromCart`'s duplicate-checkout guard was itself a check-then-write race**: two simultaneous submissions for the same cart could both read "no existing order" and both attempt to create one, with the second hitting a raw unique-constraint `QueryException` on `orders.cart_id` instead of gracefully returning the first result. Fixed by locking the `Cart` row for the duration of the transaction and re-checking inside the lock — same pattern as this project's other contested-resource Actions.
- **Two `catch (Exception)` blocks caught a wider type than intended**: `Security.php` and `RecoveryCodes.php` both guard a `decrypt()` call and should only be catching `Illuminate\Contracts\Encryption\DecryptException`. Narrowed both.
- **`LoginWithGoogle` didn't explicitly check Google's `email_verified` claim** before trusting it as a verified identifier for auto-linking — always true in practice for standard OAuth, but not checked. Now compares against the raw claim (`$googleUser->user['email_verified']`) rather than assuming it; also fixed a real edge case this exposed — if the claim is ever false and the email is already claimed by another account, the new (unlinked) account is now created without that email instead of crashing on the column's unique constraint.
- **`SafeNotifier` logged the raw exception message** on a notification dispatch failure — a theoretical leak vector if an underlying mail/SMS SDK ever embeds sensitive detail in its own exception text. This project's own rule against logging sensitive data explicitly rejects redaction as unreliable, so the message itself is no longer logged at all (only the exception class name); `report()` still routes full detail to whatever error-tracking service is configured.
- **PDF invoice generation ran synchronously** in `SettlePaymentSuccess`/`HandleLatePaymentConfirmation`'s post-commit hook — heavy file I/O with no place blocking the webhook/console process, per this project's "heavy/long-running processing must be queued" convention. Added `App\Jobs\GenerateOrderInvoicePdf` (routed to a `processing` queue) and dispatch it from both call sites instead of calling `GenerateOrderInvoice::run()` directly; the Action itself is still callable synchronously elsewhere (e.g. an admin manually regenerating an invoice).
- 12 new tests covering: OTP phone-rotation abuse and that a different IP is unaffected, the Google unverified-email edge cases (no auto-link, and the unique-constraint-safe fallback), and the invoice job's dispatch + retry/timeout hygiene. The `CreateOrderFromCart` fix relies on existing duplicate-submission coverage — true concurrent-transaction races aren't simulable in this single-process test harness, same limitation as the project's other "concurrent" tests.

### Changed — Payment gateway calls are now queued (bug-hunt: no external API call was ever queued)
- There were zero `Job` classes anywhere in the app — `HandlePaymentWebhook`, `VerifyPendingPayments`, and `ProcessRefund` all called the payment gateway's `verify()`/`refund()` directly in the request/console cycle, with no `$tries`/`$timeout`/`$backoff`/`failed()` safety net, violating this project's own "external API calls must be queued" rule. Worst case: a slow/flaky provider blocked the webhook's HTTP response (risking the provider timing out and retrying) and blocked the admin "Issue refund" action.
- Added `App\Jobs\VerifyPaymentWithGateway` (used by both `HandlePaymentWebhook` and `VerifyPendingPayments` — the exact same re-check-before-and-after-the-call guard that used to live inline now lives once, in the job) and `App\Jobs\IssueProviderRefund` (used by `ProcessRefund`, dispatched only after the refund amount is already locked/reserved synchronously — the fast, contested-resource part stays synchronous; only the slow external call is deferred). Both declare `$tries = 3`, `$timeout = 30`, `$backoff = [10, 30, 60]`, and a `failed()` handler that logs the permanent failure.
- **Behavior change**: `HandlePaymentWebhook` now marks the webhook event `processed_at` immediately after dispatching the verification job, not after the gateway call resolves — receiving and queuing the event is the idempotent action; the queued job's own `payment->status !== Pending` guard is what prevents double-processing. `ProcessRefund` now returns the `Refund` while it's still `Pending` — the Filament "Issue refund" action's success notification changed from "Refund processed" to "Refund queued" accordingly, since the gateway call hasn't necessarily completed by the time the admin sees a response.
- Both new jobs, and all 4 queued Notification classes (`OrderNotification` and its subclasses, `LowStockAlert`, `ReservationsAtRiskAlert`), are now routed to named queues (`external-api`, `notifications`) instead of the undifferentiated `default` — segmentation this project's conventions require but that didn't exist anywhere in the codebase before this change. `docs/infrastructure-deployment.md` updated with the corresponding `queue:work --queue=external-api,notifications` command and a note that payment verification/refunds — not just notifications — now depend on a running queue worker.
- 5 new tests covering: the webhook dispatches (not inline-calls) verification, `VerifyPendingPayments` dispatches one job per pending payment (respecting the existing grace period), `ProcessRefund` dispatches (not inline-calls) the gateway refund and returns a `Pending` result, and both jobs' retry/timeout/queue configuration. Existing payment/refund tests continue to pass unchanged where they exercise the full flow (the test suite's `QUEUE_CONNECTION=sync` runs dispatched jobs inline), with one test updated to check the job's actual DB effect via `->fresh()` rather than the pre-dispatch in-memory object.
- Also fixed a docblock bug found in passing: `Refund.status` was typed `string` in its model docblock despite casting to the `RefundStatus` enum (same class of bug fixed for other models earlier this session) — caught by PHPStan once the new job code compared it against enum cases.

### Fixed — Third bug-hunt round: high-risk findings
- **Review soft-delete didn't free `order_item_id` for reuse**: unlike Product/ProductVariant (already fixed), `Review.order_item_id` is a foreign key, not a string, so the same "mutate to `{value}-deleted-{id}`" trick doesn't apply. `SubmitReview`'s duplicate-check correctly scopes out soft-deleted rows, so a customer deleting their review and trying to write a new one for the same purchase hit a raw unique-constraint `QueryException` instead of working. Fixed by making `order_item_id` nullable and having `DeleteReview` null it out (inside a transaction with the soft delete) — the same "free the unique value" rule, applied via nulling instead of suffixing since it's a FK. The original value remains recoverable via activity log.
- **`ClaimGuestOrder` didn't verify the claiming email was actually verified** — a real account-linking bypass. Changing a profile email nulls `email_verified_at` but doesn't block using the new address elsewhere; `ClaimGuestOrder` matched `guest_email` to the authenticated user's `email` without checking `email_verified_at`, so a logged-in attacker could change their email to a victim's address and immediately claim the victim's guest order (and its order/address history) before ever verifying it. Fixed by requiring `email_verified_at !== null` alongside the existing checks — closing the exact gap this project's own "no auto-link on an unverified identifier" rule exists to prevent.
- **Coupon `value` wasn't required for Fixed/Percentage types**: only hidden for `FreeShipping`, so an admin could save a Fixed/Percentage coupon with a blank value. Checkout would then apply it, consume a usage slot, and silently give a $0/0% discount (`$coupon->value ?? 0` in `ApplyCouponToOrder`) with no error surfaced anywhere. Added `->required()` conditional on the coupon not being `FreeShipping`.
- 6 new tests: Review order-item reuse after delete, guest-order-claim rejection for an unverified email, and Coupon value being required for Fixed/Percentage but not FreeShipping.

### Fixed — Refund race condition and missing authorization (bug hunt, high-risk findings)
- `ProcessRefund` checked the refundable balance (`payment.amount` minus already-refunded) with no row lock, then called the payment gateway and wrote the `Refund` row in a separate, later transaction — two concurrent refund requests for the same payment (an admin double-click, or a manual refund racing `HandleLatePaymentConfirmation`'s auto-refund) could both pass the cap check and both succeed, refunding more than the original payment and over-crediting stock via the paired return movement. Fixed with the same "reserve first, confirm after" shape as `ReserveStockForOrder`: the `Payment` row is now locked (`lockForUpdate()`) inside a transaction that also inserts a `Pending` `Refund` row reserving the amount against the cap *before* the external gateway call ever happens, then a second transaction updates that same row to `Success`/`Failed` once the gateway responds. Pending refunds now count against the cap alongside Success ones, closing the exact window that made the race possible.
- The "Issue refund" table action had no `->authorize()` call at all, despite `PaymentPolicy`'s own docblock explicitly stating refunds are "gated by `update`" — anyone who could merely view the Payments resource could trigger a real refund regardless of what `update()` actually allowed. Added `->authorize(fn (Payment $record) => Auth::user()?->can('update', $record) ?? false)`.
- 4 new tests: a repeated-refunds-respect-the-cumulative-cap test (same shape as this codebase's existing stock/coupon concurrency tests), a Pending-refund-blocks-a-second-refund test proving the reservation itself (not just the eventual Success/Failed status) is what closes the race, and a policy-swap test proving the refund action's authorization actually consults `PaymentPolicy::update()` rather than relying on incidental visibility.
- Found via a 3-way parallel codebase audit (enum-comparison bugs, concurrency/money/snapshot integrity, authorization/N+1) — the remaining findings (soft-deleted Product/ProductVariant not freeing their slug/SKU for reuse, N+1 on 12 relationship columns across 8 admin tables, a few lower-risk authorization gaps, `ShippingMethod` exposing its raw bigint PK) are tracked for follow-up, not yet fixed in this change.

### Fixed — Remaining bug-hunt findings (medium/low risk)
- **Product delete bypassed slug-reuse safety**: `EditProduct`'s header `DeleteAction` and `ProductsTable`'s `DeleteBulkAction` used Filament's plain default delete, calling `$record->delete()` directly and completely bypassing `DeleteProduct` — the Action that mutates a deleted product's slug to `{slug}-deleted-{id}` so it can be reused later. `DeleteProduct` itself was correct and already tested; the admin UI just never actually called it. Added a `HasUlid`-backed `ulid` column (new migration, backfilled for any existing rows) matching the convention used by `Order`/`Payment`/`Refund`/`ProductVariant`/`Coupon`.
- 9 new tests: Product delete-routing (single + bulk + slug-reuse-after-delete), the eager-loading assertion (parameterized across all 8 resources), and the `ShippingMethod` route-key regression.

### Fixed — Attribute/term uniqueness gaps
- `Attribute.name` had no uniqueness validation at all (only `slug` did) — two attributes could both be named "Size" with different slugs. Added `->unique(ignoreRecord: true)` on the form's `name` field.

### Added — Money fields accept Cedis, not raw pesewas

- 6 existing tests updated in place (they filled Filament forms with raw pesewas values, e.g. `'price' => 3000`, which now mean GH₵3,000 instead of GH₵30 under the new field — changed to the equivalent Cedis value, e.g. `30`). ### Added — Sprint 3 (Cart & Checkout, Epic E4, plus E8 Coupons pulled forward)
- `Cart`/`CartItem` (guest-or-user, never touches stock — BRD FR-3.1) and, pulled forward from the originally-planned Sprint 7 since `CreateOrderFromCart` needed it from day one: `Coupon`/`CouponUsage` (+ `coupon_product`/`coupon_category` scope pivots, empty on both = cart-wide). Also newly built this sprint since nothing in the codebase had them yet: `Address` (nullable `user_id` for guest checkout) and `Order`/`OrderItem`/`OrderStatusHistory` — the latter finally lets `stock_reservations.order_id` get its real FK constraint, deferred since the Inventory sprint.
- `orders.cart_id` is unique — a cart converts into at most one order, ever. This is what makes `CreateOrderFromCart` idempotent: a duplicate checkout submission (double-click, back-button resubmit) returns the already-created order instead of creating a second one.
- `App\Enums\OrderStatus` and `CouponType` backed enums. `order_number` (e.g. `ORD-2026-000123`) is assigned by `OrderObserver` on creation.
- `CreateOrderFromCart` (`app/Actions/Checkout/`): reads each item's *current* variant price/details at this moment, never whatever was true when it was added to the cart (BRD Principle 8) — permanently snapshotted onto `OrderItem.item_snapshot`/`unit_price` so a later product edit/archive/delete can never change how a past order displays. Reserves stock per item via `ReserveStockForOrder` and, if a coupon code is given, applies it via `ApplyCouponToOrder` — both nested inside the one outer transaction. A guest order's `user_id` is never set from a matching `guest_email` (BRD FR-3.2a) — only `ClaimGuestOrder`, in a later sprint, can attach one, and only after the customer authenticates.
- `ApplyCouponToOrder` (`app/Actions/Checkout/`): the other of only two Actions in the system requiring row-level locking (the first being `ReserveStockForOrder`) — locks the `Coupon` row, counts actual `coupon_usages` rows (never a cached counter), and enforces `usage_limit`, `usage_limit_per_user` (by `user_id` or, for guests, `guest_email`), `min_order_amount`, `expires_at`, and product/category scope, all inside one locked transaction with 3 deadlock retries.
- `ReserveStockForOrder` (Sprint 2) updated to accept a real `Order` model instead of a raw `int $orderId` — that workaround existed only because `Order` didn't exist yet; Sprint 2's own tests updated to match.
- `AddItemToCart`, `RemoveItemFromCart`, and `MergeGuestCartIntoUser` (`app/Actions/Cart/`) — the last one isn't a documented BRD requirement, added for the expected real-world behaviour when a shopper adds items before logging in: folds the guest cart's items into an existing user cart (combining quantities) or simply reassigns the guest cart to the user if they have none yet.
- `UpdateOrderStatus` (`app/Actions/Order/`): every order status change must go through this Action so `order_status_histories` never misses an entry.
- `CartTotalsQuery`, `OrderHistoryQuery` (`app/Queries/`) — read-only, no side effects.
- Filament: `OrderResource` (no create route — only `CreateOrderFromCart` creates one; edit page only updates status + a note, routed through `UpdateOrderStatus`, never a raw column update; no delete anywhere — orders are financial/audit records) and `CouponResource`. `OrderPolicy`/`CouponPolicy` are Admin/Super-Admin-only, matching Store Keeper's inventory-only role scope from the BRD.
- Fixed a latent bug (caught by tests before it shipped): `Order` rows created without explicitly passing `discount_total`/`tax_total`/`shipping_total` left those attributes unset in memory even though the DB column defaults to `0` — a later `$order->update([...])` reusing the in-memory value could write `NULL` into a `NOT NULL` column. `CreateOrderFromCart` and `OrderFactory` now set all three explicitly.
- 24 new feature tests, including the required concurrency proofs `test_concurrent_checkout_on_last_unit_prevents_overselling` (Checkout-level, on top of Sprint 2's Inventory-level version) and `test_concurrent_coupon_use_respects_usage_limit` — both sequential rather than true cross-connection concurrency, for the same in-memory-SQLite reason noted in Sprint 2.

### Added — Sprint 4 (Payment Integration, Epic E5)
- `Payment`, `Refund` models/migrations, plus the two audit-exempt tables from `technical-design-ecommerce.md` §4g: `payment_api_logs` (every outbound call to a provider) and `webhook_events` (every inbound webhook, unique on `(provider, event_id)`). Both are written and committed on their own, before any related business-transaction processing — never nested inside it, so a rollback of order/payment bookkeeping can never erase evidence that a charge was attempted or a webhook arrived.
- `App\Enums\PaymentStatus` and `RefundStatus` backed enums.
- `App\Payments\` — a `PaymentGateway` contract, `PaymentManager` (Laravel Manager pattern, mirrors `App\Sms\SmsManager` exactly), and `MoolreGateway`/`PaystackGateway` drivers, resolved via `config/payments.php`'s channel→provider mapping (`mobile_money` → Moolre, `card` → Paystack) so both providers can be active side by side. Card/payment details are never handled directly by this platform — Paystack's hosted checkout keeps card data entirely out of PCI scope; no driver logs a raw card number.
- Payment Actions (`app/Actions/Payment/`): `InitiatePayment` (idempotent per order — reuses an existing pending payment rather than duplicating), `HandlePaymentWebhook` (verifies the provider's signature before anything else; never trusts the webhook's own reported status, always re-verifies server-side via `PaymentGateway::verify()`; idempotency is layered — the unique `(provider, event_id)` index plus a `processed_at` check, so a retried delivery never double-fulfills), `ProcessRefund` (refund amount capped against the payment's amount minus whatever's already been refunded — cross-row arithmetic the database can't constrain — restores stock via a `return` `StockMovement`), `VerifyPendingPayments` (scheduled every 2 minutes, the polling fallback for a slow/missing webhook), `HandleLatePaymentConfirmation` (a payment confirming after its reservation already expired either fulfills directly if stock is still available, or auto-refunds and cancels the order if not), and `SettlePaymentSuccess` (the shared success-handling logic both the webhook handler and the poller funnel through, so whichever arrives first "wins" and neither double-processes).
- `POST /webhooks/payments/{provider}` — thin controller, all logic in `HandlePaymentWebhook`; exempted from CSRF verification (a payment provider can't obtain a token — the driver's signature check is this endpoint's actual authenticity gate).
- Filament: read-only `PaymentResource` (no create/edit — only `InitiatePayment` creates a payment, only the webhook/polling/late-confirmation Actions change its status) with an "Issue refund" table action calling `ProcessRefund`, and a read-only `RefundsRelationManager`. `PaymentPolicy`/`RefundPolicy` are Admin/Super-Admin-only, same scope as Order/Coupon.
- `PaymentManager` registered as a container singleton in `AppServiceProvider` (mirroring `SmsManager`) — required for `PaymentManager::extend()`-registered test doubles to actually be seen by Actions resolving the manager via constructor injection.
- 14 new feature tests against a `FakePaymentGateway` test double registered via the same public `PaymentManager::extend()` point a real new provider would use — covering initiation idempotency, outbound call logging, webhook signature rejection, duplicate webhook delivery, the mutual idempotency of polling vs. webhook confirmation, both branches of late payment confirmation, and the refund-amount cap (including after a prior partial refund).

- `App\Enums\ShipmentStatus` backed enum.
- `GenerateOrderInvoice` (`app/Actions/Order/`): renders a PDF receipt via `barryvdh/laravel-dompdf` (already installed since Sprint 0) reading exclusively from `Order`'s own totals and each `OrderItem.item_snapshot` — never live `Product`/`ProductVariant` data, so a regenerated invoice for an old order looks identical no matter what's since happened to the catalog. - `ShippingMethodPolicy` added; no separate policy for `Shipment` since it isn't its own Filament resource (managed entirely through the Orders table actions).
- 7 new feature tests, including `test_invoice_rendering_does_not_read_live_product_data` (deletes the live product/variant entirely before rendering, proving the invoice view only ever reads `item_snapshot`) and coverage of both `ClaimGuestOrder` guard conditions (email mismatch, already-attached order).

- Laravel's built-in `notifications` table (database channel), enabling both in-account notification history for customers and the Filament admin notification bell (`->databaseNotifications()` + 30s polling on the admin panel).
- `product_variants.low_stock_threshold` (nullable, falls back to a new `store_settings.low_stock_threshold`, default 5) — neither field existed anywhere before this sprint; both editable via Filament (the variant form, and the Store Settings page).

- `App\Notifications\OrderNotification` (shared base for the four order-lifecycle notifications) selects channels per-recipient: phone present → sms, email present → mail, both → both — a Google-only customer with no phone never gets an sms attempt.

- `App\Notifications\Support\StaffRecipients` resolves staff by role while tolerating a role that hasn't been seeded yet in a given deployment (`Spatie\Permission`'s `RoleDoesNotExist` would otherwise turn a missing role into a hard failure of ordinary stock-movement recording).

All fire only `->afterCommit()` where there's a transaction to wait for.
- Two staff-facing notifications: `LowStockAlert` to every Store Keeper — fired in real time by `RecordStockMovement` the moment a variant's stock *crosses* its threshold (not on every subsequent sale while already low, to avoid spamming), plus a new daily-scheduled `CheckLowStockLevels` sweep as a safety net for anything the real-time check might miss. `ReservationsAtRiskAlert` to every Admin/Super Admin — closes a gap noted back in the Inventory sprint, where `AdjustStockWithReservationCheck` flagged reservations `at_risk` but never actually notified anyone.
- Fixed a second instance of the "unrefreshed attribute after `firstOrCreate`" bug class (first found in Sprint 3 on `Order`): `StoreSetting::current()` now re-fetches after creating a fresh row, so `low_stock_threshold` (and any future DB-default column) reliably reflects what's actually in the database rather than an unset in-memory attribute.
- Fixed two pre-existing flaky tests unrelated to this sprint's changes: `ProductVariant::factory()->create()` defaults to a random 0–100 stock, and two `CheckoutTest` cases that reserve stock could occasionally roll 0 and fail — both now pass an explicit `stock`.
- 10 new feature tests covering all four customer notifications (including the guest on-demand routing and the email-only fallback for a phone-less customer), both staff alerts, the crossing-point de-duplication for low-stock alerts, and the daily sweep.

### Changed — notifications are now queued
- All six notification classes implement `ShouldQueue` (`QUEUE_CONNECTION=database`, already configured). Matters most for `HandlePaymentWebhook`: it's a synchronous HTTP endpoint the payment provider calls, and blocking on an SMS/email round-trip there risked the provider timing out and retrying the webhook. `SafeNotifier`'s docblock updated to reflect that it now guards dispatch-time failures (the queue push itself); real delivery failures happen later inside the queue worker, governed by the queue's own retry/`failed()` handling. Requires an actual queue worker running in production — noted as the user's responsibility to provision (e.g. via a cron-driven `schedule:run` + supervisor, or a dedicated worker process).

### Changed — Filament navigation polish
- Every resource now has a distinct Heroicon (previously most shared a generic placeholder) and a `navigationGroup`, organizing the sidebar into **Catalog** (Products, Categories, Brands), **Inventory** (Stock Movements, Stock Reservations), **Sales** (Orders, Payments, Coupons, Shipping Methods), **Reviews**, **Reports** (Activity Log), and **Settings** (Store Settings).

### Added — Development seed data
- `database/seeders/{RoleSeeder,UserSeeder,StoreSettingSeeder,ShippingMethodSeeder,CatalogSeeder,CouponSeeder,OrderSeeder}.php`, orchestrated from a rewritten `DatabaseSeeder`.
