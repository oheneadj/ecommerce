# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed — sharing a product link showed the store logo instead of the product photo
- No Open Graph or Twitter Card meta tags existed anywhere in the app — with no `og:image`, a link-preview crawler (WhatsApp, Facebook, iMessage, etc.) fell back to whatever image it could find on the page, which in practice meant the header logo (the first `<img>` in the DOM on every page) instead of the thing actually being shared. `partials/head.blade.php` now renders `og:title`/`og:description`/`og:image`/`og:type` and matching Twitter Card tags on every page, with sane store-level defaults (logo, tagline) and per-page overrides.
- Separately, the product page's `<title>` was hardcoded to the generic string "Product" — the outer page wrapper never had access to the resolved product, only the Livewire component nested inside it did. Now resolves the product once (cheaply, read-only) in the outer wrapper so the real name/description/primary image are present in the initial server-rendered HTML, which is what link-preview crawlers actually see (they don't wait for Livewire to hydrate).
- Also wired `StaticPage.meta_description` into the same `og:description` mechanism — captured on the admin form since an earlier sprint but never actually rendered anywhere until now.
- 8 new tests.

### Fixed — invoice download disappeared once an order shipped (full-system bug hunt, 3/7)
- `OrderDetailPage::canDownloadInvoice()` required `status === Paid` exactly, so the "Download invoice" button vanished the moment staff advanced the order to Processing/Shipped/Delivered — even though the invoice PDF was still sitting there and the admin panel's own equivalent (`OrderRecordActions::downloadInvoice()`) had no such restriction. Now gates on `invoice_path !== null` alone, matching the admin panel exactly — `invoice_path` is only ever populated once `SettlePaymentSuccess` generates it, so this already implies the order was paid.
- 1 new regression test (a Shipped order can still download its invoice); existing paid/unpaid cases re-verified.

### Fixed — concurrent stock decrements could drive stock negative (full-system bug hunt, 2/7)
- `RecordStockMovement`'s negative-stock guard read `$variant->stock` from PHP memory with no row lock, while the actual decrement was a separate atomic SQL statement — two concurrent calls for the same variant (e.g. two `HandleLatePaymentConfirmation::fulfill()` calls, which is documented as an accepted unlocked check-then-act) could each read the same pre-decrement stock, both pass the check, and both apply, leaving stock negative despite the class's own docblock promising this couldn't happen.
- Now locks the variant row (`lockForUpdate()`) for the duration of its own transaction, so the check and the decrement are atomic — matching `ReserveStockForOrder`/`ApplyCouponToOrder`'s existing pattern for the other two contested resources in this system. Safe to call from inside a caller's own outer transaction (Laravel savepoints); the caller's passed-in `$variant` instance is kept in sync with the new stock value, since `AdjustStockWithReservationCheck` reads it immediately afterward.
- Updated stale docblocks on `ReserveStockForOrder`/`ApplyCouponToOrder`/`AdjustStockWithReservationCheck` that claimed only two Actions (now three) needed locking, or that this class had none.
- 2 new tests: a sequential boundary-depletion regression (this suite's existing convention for proving a locking invariant, since true parallel threads aren't exercisable against the test SQLite connection) and one confirming the caller's variant instance stays in sync.

### Fixed — disabled customer accounts could still log in (full-system bug hunt, 1/7)
- `disabled_at` only ever gated the Filament admin panel (`User::canAccessPanel()`) — a disabled customer account could still authenticate via password, phone OTP, or Google with zero effect. A Super Admin disabling an account after a fraud/abuse report didn't actually block anything.
- Password login: added a `Fortify::authenticateUsing()` override (Fortify's own documented extension point) that rejects disabled accounts with a normal validation error, alongside its existing credential check — the rest of Fortify's pipeline (throttling, 2FA challenge) is untouched.
- Phone OTP and Google: `VerifyOtp`/`LoginWithGoogle` now check `disabled_at` on the resolved account before calling `Auth::login()`, throwing a new shared `App\Exceptions\AccountDisabledException` — caught by `PhoneLogin` (inline error) and `GoogleAuthController` (redirect with a flash message), matching this app's existing per-entry-point exception-handling convention.
- 6 new tests covering all three login paths, both disabled and still-working-when-enabled.

### Docs — Store Keeper's product catalog access is intentional, not a bug
- A prior audit flagged Store Keeper being able to create/edit full product records (name, description, price, category, brand) as contradicting the BRD's "inventory and catalog stock" wording. Confirmed with the project owner: this is deliberate — a small store's owner delegating day-to-day catalog data entry to a Store Keeper is a normal operating model, and a product's own fields carry no access to money movement (orders/payments/coupons stay fully out of reach regardless, unaffected by this). Updated the BRD's role table and business rule 7 to describe actual/intended behavior; product deletion remains Admin/SuperAdmin-only, unchanged. 3 new tests documenting the intended access as an asserted contract rather than an untested gap.

### Fixed — a genuinely free order ($0 total) had no way to complete checkout
- `InitiatePayment` always called the payment gateway, which rejects zero-amount transactions — a free/giveaway product, or a 100%-off coupon with no tax/shipping, produced an order that could never be paid for; every attempt failed at the gateway. Now settles a $0 order directly through the same `SettlePaymentSuccess` fulfillment path a real successful payment uses (stock consumed, order marked Paid, invoice generated, confirmation sent), with no gateway call and no `payment_api_logs` entry for a call that never happened. 3 new tests.

### Fixed — admin-panel phone fields could bypass normalization entirely
- Staff phone, a staff member's own profile phone, and the store's contact phone all normalized only via a client-side Livewire blur event — skippable via Enter key, autofill, or a fast form fill. A submission that skipped it persisted the raw local-format number verbatim instead of the canonical E.164 form every other phone input path stores, silently breaking SMS delivery and uniqueness matching. Added `dehydrateStateUsing()` to all three fields, which runs server-side on every save regardless of whether blur ever fired. 2 new tests.

### Fixed — a Filament `visible()`-only gate didn't actually block a payment view action from being invoked directly
- The Payments relation manager's `ViewAction` (surfacing raw provider callback metadata) was restricted to Super Admin via `visible()` alone, which hides the button but doesn't stop a crafted request from mounting the action directly — unlike the standalone Payments resource's own `ViewAction`, this one renders inline via an explicit `->schema()` with no page-route `canAccess()` to fall back on. Added `authorize()` to both this action and the standalone table's equivalent (defense-in-depth, since the latter is already backstopped by its page). 3 new tests.

### Fixed — two dependency advisories with high-severity DoS issues
- `composer audit` flagged `league/commonmark` (4 high-severity DoS advisories) and `guzzlehttp/guzzle` (a high-severity host-check bypass); `npm audit` flagged `nanoid` (high) and `postcss` (moderate). Updated to patched versions; full test suite and frontend build both verified green afterward.

### Fixed — a dashboard widget loaded the entire customer table into PHP to compute a stat
- `CustomerSegmentsWidget` (via `DashboardMetricsQuery::customerSegmentsInRange()`) pulled every customer row into memory just to bucket order counts with `->filter()` — a full-table load on every dashboard render that gets worse as the customer base grows. Rewritten as a single SQL aggregate query. 5 new tests, including one asserting the query count.

### Fixed — three dashboard charts issued one (or two) queries per day in a custom date range
- `CustomerGrowthWidget`, `MonthlyRevenueChart`, and `OrdersYearOverYearWidget` each looped over every day in a selected range calling a single-day query per iteration — up to 120 queries for a 60-day range from one ordinary admin filter action. New `ordersCountByDay()`/`newCustomersCountByDay()`/`revenueByDay()` on `DashboardMetricsQuery` group by day in one query (two for revenue: payments and refunds) regardless of range length. 8 new tests.

### Fixed — two dashboard widgets hand-rolled money formatting instead of using the established helper
- `DashboardStatsOverview` and `ProductsOverviewWidget` built `'GH₵'.number_format(...)` directly instead of the `HasFormattedMoney` trait every other money display in the app uses — not currently wrong, but a silent divergence that would mis-render if the store currency were ever made configurable. Both now use the shared trait.

### Fixed — two Actions accepted a zero/negative quantity with no guard
- `AddItemToCart` had no `quantity > 0` check (inconsistent with `UpdateCartItemQuantity`'s explicit handling) and `ReserveStockForOrder` silently accepted `quantity = 0`, creating a meaningless reservation row. Both currently unreachable through the UI (every caller hardcodes a positive quantity), so latent rather than live — closed for consistency and to guard any future caller. 6 new tests.

### Fixed — StoreSetting's singleton row could race into two competing rows
- `StoreSetting::current()`'s `firstOrCreate([])` is a SELECT then an INSERT, not atomic — two concurrent first-touch requests against an empty table (e.g. two admin tabs loading Store Settings right after a fresh deploy) could both see no row and both insert, permanently orphaning one. New `singleton_key` column with a unique constraint is what actually prevents a second row from ever existing; `current()` now catches the resulting constraint violation on the losing request and re-fetches the winner's row. 4 new tests.

### Added — a configurable store display timezone, used on customer-facing order timestamps
- Order history, order detail, and invoice PDFs showed `created_at` in raw UTC with no conversion — a late-night order could display on the wrong calendar day for a store operating outside UTC. New `StoreSetting.timezone` (admin-configurable, defaults to UTC) and `Order`/`OrderStatusHistory::placed_at` accessors (via a shared `DisplaysInStoreTimezone` trait, mirroring the existing `HasFormattedMoney` pattern) convert at the display boundary only — everything is still stored and computed in UTC everywhere else, per this project's own convention. 4 new tests.

### Fixed — the wishlist heart on every product card issued its own database query
- Each product-card `WishlistButton` is a separate Livewire component instance; with no cross-instance cache, a listing page with N cards ran N `wishlist_items` existence queries for a logged-in customer — invisible to `Model::preventLazyLoading()` since it's component composition, not an Eloquent relation traversal. Now memoized per request via the array cache store, invalidated on toggle. 1 new test proving the query count no longer scales with the number of cards on the page.

### Fixed — every admin "Export" bulk action crashed, and customer names could carry a CSV/Excel formula-injection payload
- Every `ExportBulkAction` (Customers, Products, Orders, Payments, StockMovements) passed plain column-name strings to `withColumns()`, which only accepts `pxlrbt\FilamentExcel\Columns\Column` instances — clicking "Export" on any of them fataled ("Call to a member function getName() on string"). Fixed across all five.
- Separately: the Customers export's `name` column (and Products' `name`, StockMovements' `note`) is free text a lower-trust user can set — a customer setting their display name to `=HYPERLINK("http://evil.example","x")` would have that formula execute the moment an admin opened the exported file in Excel. New `App\Support\SanitizesExportFormulas` prefixes a literal quote on any cell starting with `=`, `+`, `-`, or `@` (the standard mitigation), wired into all three free-text columns. 13 new tests.

### Fixed — registration and password-reset requests had no rate limiting
- Unlike login/2FA/OTP/search (all already throttled), `/register` and `/forgot-password`/`/reset-password` carried no throttle at all in Fortify's own route file — a script could mass-create accounts, or flood a victim's inbox with reset links / probe which emails exist, at unbounded rate. Added a `guest-auth-forms` limiter applied globally to the `web` middleware group, branching by route name (`Limit::none()` for everything else, so it has zero effect elsewhere). 4 new tests.

### Fixed — coupon codes at checkout had no brute-force protection
- `CheckoutPage::applyCoupon()` called into a DB lookup with no throttle on every attempt. `PreviewCouponDiscount` now rate-limits to 10 attempts per 5 minutes per cart. 2 new tests.

### Fixed — a small image file could exhaust server memory on upload, and a corrupt one could crash instead of falling back
- `ConvertImageToWebp` never checked pixel dimensions before decoding — a small-file-size, huge-resolution image (a "decompression bomb") could exhaust PHP's memory_limit on the synchronous admin upload request. Now rejected via a cheap header-only `getimagesize()` check before any decode is attempted (`config('media.max_image_pixels')`, env `MEDIA_MAX_IMAGE_PIXELS`).
- Separately, the action only caught `Illuminate\Image\ImageException`, but the underlying decode call isn't wrapped by Laravel's Image component — a corrupt (or bomb-triggered) file threw Intervention Image's own exception hierarchy uncaught instead of hitting the intended "keep the original" fallback. Now caught alongside. 4 new tests.

### Fixed — backup restore didn't validate symlink entries in the archive
- `ZipArchive::extractTo()` already blocks `..`-based path traversal at the PHP extension level, but still extracts symlink entries verbatim without validating their target (CVE-2014-9767) — only exploitable if an attacker already has write access to the Google Drive backup folder, but a restore is destructive enough to fail closed regardless. Now rejects any archive containing a symlink entry before extraction. 1 new test.

### Fixed — guest carts could grow without bound
- `ResolveCurrentCart` creates a fresh, empty cart row for every guest visit with no live cart — nothing ever cleaned these up, so a script hitting `/cart`/`/checkout` repeatedly with cookies stripped between requests could grow the table indefinitely. New daily-scheduled `PruneStaleGuestCarts` deletes guest carts older than the session lifetime that were never converted into an order. 5 new tests.

### Fixed — a stolen session survived the exact security actions meant to lock it out
- Changing your password, enabling/disabling 2FA, or removing a passkey never invalidated any other active session — an attacker holding a stolen-password session kept full account access even after the legitimate owner changed their password or turned on 2FA specifically to lock them out. New `App\Actions\Auth\LogOutOtherSessions` deletes every other `sessions` row for the user; wired into all five security-relevant actions in `App\Livewire\Settings\Security`. 4 new tests.

### Fixed — staff role changes were invisible to the admin activity log
- `EditStaff::handleRecordUpdate()` applies a role change via `syncRoles()`, which writes straight to the `model_has_roles` pivot table and never fires Eloquent's save/update events — so `User`'s `LogsAdminActivity` hooks never saw it. A Super Admin promoting or demoting a staff member left zero audit trail, unlike every other staff-account mutation (the disable/enable toggle was already correctly logged). Now logs an explicit `role changed` entry, attributed to the acting admin, only when the role actually changes. 2 new tests.

### Fixed — product search could silently return incomplete or inconsistent results at scale
- `SearchProducts`' candidate query capped at 300 rows with no `ORDER BY` — an unordered `LIMIT`'s row set is implementation-defined, so once the catalog exceeds 300 active in-stock products, a genuinely matching product could intermittently fail to appear in search, with no data change between requests. Now ordered deterministically by `id` before the limit. 1 new test.

### Fixed — order status could skip required states, and cancelling a paid order never restocked
- `UpdateOrderStatus` accepted any status change with no validation — both the admin's single-record and bulk "Update status" actions offered the full status list regardless of the order's current state, so an order could jump `Pending` straight to `Delivered` (skipping payment/stock decrement entirely) or move backwards out of a later status. `OrderStatus::allowedNextStatuses()` now defines the legal transition graph; anything outside it throws `InvalidOrderStatusTransitionException`, caught in the admin UI as a clean notification instead of an uncaught exception. The single-record action's Select is also now restricted to only the record's actual valid next statuses.
- Separately: cancelling an order that had already been `Paid`/`Processing`/`Shipped` (stock already decremented on settlement) never returned that stock to inventory — the goods were gone from the count forever. `UpdateOrderStatus` now records a `Return` stock movement for every item when cancelling from a status where stock was known to be decremented, exactly once (the new transition guard makes `Cancelled` terminal, so this can't double-fire for the same order).
- 12 new tests; 2 existing tests updated to start from a valid pre-`Delivered` status rather than exercising the transition-skip this fix closes.

### Fixed — bulk SMS blasts had no cost cap or rate limit
- `SendCustomerNotification`'s bulk SMS channel could queue one SMS job per matched customer with no maximum and no confirmation of estimated cost — a single "All customers" click could trigger real, uncapped SMS spend. `BroadcastMessageToCustomers` now rejects an SMS broadcast over `config('sms.broadcast_max_recipients')` (env `SMS_BROADCAST_MAX_RECIPIENTS`, default 500; email/in-app aren't capped, they carry no per-send cost) and rate-limits any admin to 5 broadcasts per 10 minutes regardless of channel. 7 new tests.

### Fixed — documented product image/variant limits were never actually enforced
- `PRODUCT_MAX_IMAGES`/`PRODUCT_MAX_VARIANTS` were documented in `.env.example` but never read anywhere — the only real cap was an unrelated hardcoded `maxFiles(10)`, and variant generation had no limit at all (a large attribute selection could create hundreds of variants in one click). Both are now wired to `config('media.product_max_images'/'product_max_variants')` and enforced server-side — on the image upload field's total (not just per-upload), on `GenerateProductVariants`' bulk generator, and on the single "Add variant" action — each rejecting past the limit with a clean notification instead of silently allowing it. 5 new tests.

### Fixed — deleting a category with products crashed; deleting an attribute cascaded silently
- Deleting (or bulk-deleting) a Category still assigned to Products threw an unhandled `QueryException` (a raw 500) — `products.category_id` is `restrictOnDelete()` at the DB level, but nothing checked for that before attempting the delete. Both the single-record and bulk delete actions now check first and show a clean "still has products assigned" notification instead.
- Deleting an Attribute cascades through every `attribute_terms`/`attribute_product`/variant-term-assignment row referencing it, with no warning of the actual impact. Both delete actions now show the real product/variant counts affected in the confirmation modal before proceeding, rather than a generic "are you sure?".

### Fixed — a stray directory at `public/storage` could pass the storage-symlink health check while uploads still 404ed
- `StorageIsWritableAndLinked` accepted a plain directory as equivalent to a real symlink (`is_dir()` alongside `is_link()`), and its write-probe wrote directly to `storage/app/public`, bypassing `public/storage` entirely — so a broken deploy could show green on the System Health dashboard while every uploaded image 404ed for visitors. Now requires an actual symlink whose target resolves to `storage/app/public`. 2 new tests.

### Fixed — the 24-hour health-alert snooze could suppress an unrelated new critical failure
- The snooze was a single global timestamp with no record of which failure(s) it was taken against — snoozing a known, low-severity issue (e.g. an unconfigured SMS provider) silenced notification for anything else that broke in the next 24 hours too, including something as serious as payments failing. New `store_settings.health_alerts_snoozed_failures` column records the exact failing-check labels at snooze time; `SendCriticalHealthAlert` now only suppresses when every currently-failing check is covered by what was actually snoozed — a genuinely new failure still alerts immediately. 4 new/updated tests.

### Fixed — SMS delivery logs always attributed the send to Moolre, even when GiantSMS was active
- `sms_api_logs.provider` was hardcoded to `'moolre'` in all three SMS call sites (`RequestOtp`, `SendCustomerSms`, the `sms` notification channel), regardless of which driver `SmsManager` actually resolved — every log entry misattributed delivery to the wrong provider whenever a store had GiantSMS configured as active, breaking reconciliation/debugging. Each now reads the real active driver from `SmsManager::getDefaultDriver()`. 3 new tests.

### Fixed — payment settlement race could double-decrement stock and double-fulfill an order
- `SettlePaymentSuccess` checked whether a payment was still Pending, and whether its stock reservations were still active, entirely outside any lock — a webhook delivery racing the polling sweep (or a duplicated job dispatch) could both pass those checks and both proceed to fulfill. `RecordStockMovement` then unconditionally decremented stock even when the reservation update it followed was a no-op, so the same physical unit could be sold twice.
- The entire settlement — including the fallback to `HandleLatePaymentConfirmation` when a reservation already expired — now runs inside a single transaction that takes `lockForUpdate()` on the payment row first and re-checks it's still Pending before doing anything. Whoever gets the lock first settles the payment; a concurrent second call sees a non-Pending status and no-ops.
- 1 new test (`test_settling_the_same_payment_twice_only_decrements_stock_once`) — true cross-connection concurrency can't be exercised against the in-memory SQLite test database (same limitation `InventoryManagementTest`'s own concurrency test already documents), so this proves the invariant the lock guarantees instead: a second settlement attempt for an already-settled payment is a genuine no-op.

### Fixed — stock could go negative via an ordinary admin stock adjustment
- `RecordStockMovement` — the single write path for every stock change — only rejected a zero quantity; it never checked that a movement wouldn't leave stock below zero. A `Damage`/`Adjustment` movement larger than the current stock (a data-entry error, not a real physical count) drove `product_variants.stock` negative, which then poisoned low-stock alerts and available-stock math.
- New `NegativeStockException`, thrown before any movement is written or stock is touched. 3 new tests.

### Fixed — backups silently never run in production
- `RunBackupJob` dispatches to the `backups` queue, but this project's documented production worker command (`docs/infrastructure-deployment.md`) and local dev queue listener (`AppServiceProvider::configureDevQueueWorker`) never listened to it — every scheduled and manual backup queued forever and never executed, with the admin only ever seeing a `BackupRun` row stuck at `Running`. Both now include `backups`.
- The "only one backup ever runs at a time" guarantee `RecordSuccessfulBackup`/`RecordFailedBackup`/`BackupRun::scopeRunning()` all relied on was actually just a check-then-act read with no lock — a scheduled run and a manual "Run now" click could race, corrupt the shared temp directory, and leave a `BackupRun` row stuck at `Running` forever. `RunBackupJob` now holds a cache lock for its entire run; a concurrent dispatch is a genuine no-op rather than a second run. 2 new tests.

### Fixed — connecting Google to a phone-only account could crash on an email collision
- `LinkAccountIdentifier` set a phone-only user's email straight from their Google account with no uniqueness check, unlike the equivalent `LinkPhoneToAccount` flow — if that email already belonged to a different existing account, the save threw an uncaught `QueryException` (500) instead of a clean error. Now pre-checked, with a `users_email_unique` constraint violation as a race-safe fallback, both raising the new `GoogleEmailAlreadyTakenException`. 2 new tests.

### Fixed — merging a guest cart into an account cart could exceed stock
- `MergeGuestCartIntoUser` combined quantities from both carts with no cap against the variant's stock, unlike `AddItemToCart`'s explicit stock invariant — two carts each individually within stock at the time their items were added (one built while logged out, one while authenticated) could combine to more than physically exists. Now capped at current stock, same as every other write path. 1 new test.

### Added — comprehensive project README
- Added `README.md`: tech stack, feature overview, setup instructions (including gaps not covered by `composer run setup` — `php artisan storage:link`, `php artisan app:create-super-admin`, the required queue worker and scheduler cron entry), environment variable reference, and a documentation index linking every file under `docs/`.

### Fixed — confusing "empty cart" after a failed/pending payment
- A customer whose payment failed or was still being confirmed could land back on an empty-looking `/cart` or `/checkout` with no explanation. Root cause: `Cart::scopeOpen()` correctly closes a cart the moment its order has a `Pending` payment (by design, so a live payment can't be double-submitted against), but nothing told the customer *why* — `ResolveCurrentCart`/`GetCurrentCart` just silently handed back a brand-new empty cart instead.
- `placeOrder()`'s one remaining special case — a payment failing synchronously at initiation — previously just showed an inline checkout error and left the customer stuck there. It now redirects to the order's own confirmation page like every other outcome already did (`respondToPaymentInitiation`'s existing fallback branch already does the right thing once the special case is removed — no new redirect logic needed there).
- `orders.confirmation` (the page every checkout outcome — success, popup, redirect, or Moolre's phone-prompt flow — already funnels to) is now actually status-aware instead of a fixed "Thank you!" regardless of outcome: pending shows a live-polling "confirming your payment" state, failed shows the reason and a **retry** button (identical for guests and authenticated customers — reaching this page at all already requires the order's own unguessable URL), success shows the existing thank-you. Extracted the shared pending/failed/retry logic (previously only on the authenticated-only `OrderDetailPage`) into `App\Livewire\Storefront\Concerns\TracksPaymentStatus`, used by both pages instead of duplicating it.
- New `App\Actions\Checkout\FindRecentUnresolvedOrder`: when `/cart` or `/checkout` would otherwise show an empty cart, checks first whether that's because the customer's most recent cart closed on an unresolved (`Pending`/`Failed`-only) order, and redirects to that order's now-informative confirmation page instead. A genuinely empty cart still renders normally, with a small nudge toward order history for authenticated customers as a last-resort fallback.
- 19 new/updated tests across `OrderConfirmationPage`, `OrderDetailPage`, `CheckoutPage`, `CartPage`, and the new Action.

### Added — dismissible popup announcements, alongside the (still non-dismissible) banner
- Announcements now have a `type`: `banner` (top of page, never dismissible — unchanged) or `popup` (centered modal, dismissible). Both can be running and shown at the same time — they don't compete for the same slot; each type independently picks its own highest-priority currently-matching announcement.
- New `App\Livewire\Storefront\AnnouncementPopup` component + `<x-modal>`-based view (reusing the existing modal component rather than building a new one). Dismissing a popup is permanent for that visitor, same "no snooze/re-show" rule popups now uniquely have — closing it (X button, backdrop click, or Escape) sets `dismissed_at` on their `AnnouncementView` row.
- Extracted the matching logic both components share (schedule, active flag, audience, optional dismissed-exclusion) into `App\Services\AnnouncementMatcher`, so `AnnouncementBanner` and `AnnouncementPopup` aren't two copies of the same query.
- `announcement_views.dismissed_at` is back (removed in the previous entry when banners lost their dismiss button) — now scoped to popups only; a banner's view rows never have it set, since there's no code path that could set it for one.
- 8 new tests.

### Added — "Connect Google" and "Set password" on Profile and Security (parts 3+4/4)
- Every account can now add whichever login method it started without: an email+password customer can connect Google or add a verified phone (already existed); a phone/Google-only customer can now set a password for the first time. Both actions appear on **both** Profile and Security settings pages via a shared partial, since either page is a reasonable place for a customer to land looking for them.
- "Connect Google" reuses the already-safe `LinkAccountIdentifier` flow from part 2 — no new linking logic, just a discoverable button where none existed before. Shows a "Connected" badge once linked; `/login/google` now returns to whichever page the button was clicked from (Profile or Security) instead of always the dashboard.
- "Set password" requires a verified email first (the forgot-password takeover risk discussed in the audit) — shows a clear explanatory message instead of the form when the email isn't verified yet, or nothing at all once a password already exists (Security's existing "Update password" card, which needs `current_password`, only shows once one exists).
- New `App\Livewire\Concerns\ManagesAdditionalLoginMethods` trait shared by `Profile`/`Security` — single source of truth for `hasGoogleLinked`/`hasPassword`/`canSetPassword` and the `setInitialPassword()` action, avoiding duplicating this logic across both pages. New shared `login-methods` Blade partial for the markup itself.
- 10 new tests across both pages.

### Fixed — Google login could silently hand over access to a different customer's account (part 2/4)
- `LoginWithGoogle` auto-linked a first-time Google sign-in onto an existing account purely by email match, checking only Google's own `email_verified` claim — never whether the *existing* account's email had ever been independently verified. A customer who self-typed (and never verified) someone else's real email into Profile settings could have that account silently handed to whoever actually owns that email's Google account the next time they signed in with Google — full access to someone else's orders, addresses, everything. Now requires both sides independently verified before auto-linking (CLAUDE.md's identifier-linking rule).
- When the existing account's email isn't verified, the login is now refused with `GoogleEmailConflictException` instead — a fresh verification email is sent automatically (rate-limited, 1/5min, since this now fires from an unauthenticated context) and the customer is redirected to phone login with a clear message pointing at two ways out: verify the email and retry Google (both sides then verified, auto-link proceeds), or log in with their original method and connect Google from settings.
- Fixed a second, unrelated bug found while wiring the above: `AccountIdentifierAlreadyLinkedException` (thrown when linking a Google account already claimed by a different customer) was never caught in `GoogleAuthController` — this reachable case previously surfaced as an uncaught 500, not a message.
- New `App\Exceptions\GoogleEmailConflictException`; `/login/google` now accepts a `redirect_to` param so the authenticated "connect Google" flow returns to wherever it was started from, not always the dashboard. 9 new tests.

### Fixed — email verification was completely non-functional (part 1 of the auth edge-case audit)
- `App\Models\User` never implemented Laravel's `MustVerifyEmail` trait, meaning `hasVerifiedEmail()`/`sendEmailVerificationNotification()` were undefined on the model — Fortify's own email-verification routes (`verification.notice`, `verification.verify`) call these internally, so `tests/Feature/Auth/EmailVerificationTest.php` was **already failing** before this fix (confirmed: 4/4 pass now, 0/4 before). Added the trait deliberately, not the `Illuminate\Contracts\Auth\MustVerifyEmail` *interface* — the `verified` route middleware already applied to every account route stays a no-op, so no customer's general account access changes.

### Fixed — payment webhook/verification security gaps found against Paystack's own docs
- **Amount was never cross-checked on payment verification.** Paystack's docs are explicit that a "success" status alone isn't enough — the confirmed amount should be checked against what's actually owed too. Previously `SettlePaymentSuccess` was reached purely on `status === Success`, with no comparison against the order's expected total anywhere in the chain. `PaymentVerificationResult` gained an `?int $amount` field (null when a driver's verify endpoint doesn't expose one — treated as "can't check," never as a mismatch, so a driver lacking the field never false-blocks every payment through it), populated in both `PaystackGateway::verify()` (`data.amount`, confirmed from Paystack's docs) and `MoolreGateway::verify()` (best-effort — Moolre's exact response shape for this field wasn't live-verified). `VerifyPaymentWithGateway` now rejects (treats identically to a gateway-reported failure) rather than fulfills a "successful" payment whose confirmed amount doesn't match the payment's expected amount.
- **Added a soft, log-only IP check for Paystack webhooks**, per their documented recommendation to whitelist their sending IPs (`52.31.139.75`, `52.49.173.169`, `52.214.14.220`) in addition to signature verification. Deliberately never blocking — the HMAC signature check is what actually proves authenticity (nobody can forge one without the secret key), and Paystack's IPs can rotate without notice, so a hard block here would risk silently dropping legitimate payment confirmations for a check that isn't load-bearing. A request from an unrecognized IP is logged (`Log::warning`) and still fully processed. Providers with no published IP list (Moolre) are simply skipped, never flagged.
- Confirmed everything else already matched Paystack's documented requirements: HMAC-SHA512 signature verification via `hash_equals`, immediate `200` response with real work deferred to a queued job (well inside their 30s timeout), idempotency via a unique `(provider, event_id)` constraint plus a `processed_at` check, and never trusting the webhook payload's own reported status over a server-side `verify()` call.

### Fixed — Queued jobs on named queues never ran in local dev
- `composer run dev` (Laravel's built-in `artisan dev`) starts a `queue:listen` process with no `--queue` flag, which only services the `default` queue. This project deliberately segments every job onto a named queue (`emails`/`sms`/`notifications`/`processing`/`external-api`, per CLAUDE.md §15) so time-sensitive work never queues behind slow external-API work — but that segmentation meant the dev queue listener was never actually working any of them. 38 jobs had piled up undelivered, including a just-sent customer broadcast notification, order confirmations, and low-stock alerts going back to when queue segmentation was introduced.
- `AppServiceProvider::configureDevQueueWorker()` re-registers the `queue` dev command (`DevCommands::artisan(...)`) with `--queue=notifications,emails,sms,processing,external-api,default` — a userland registration wins over the framework's default per `DevCommands::resolvePriority()`. Drained the existing backlog manually (`php artisan queue:work --queue=... --stop-when-empty`); 33 succeeded, 5 pre-existing SMS jobs failed on a missing local Moolre API key (a separate, expected local-env gap — not something to paper over with fake credentials).
- Requires restarting any already-running `composer run dev` process to take effect (it's a boot-time provider registration).

A fast drag leaves the thumb's DOM position one Alpine reactivity tick behind the cursor, so on release the browser's synthetic `click` event lands on the track rather than the thumb (`@click.stop` on the thumb never runs) and fires a second, slightly different jump immediately after the drag already committed — visible as the slider "moving by itself" right after letting go. Unified both interactions into a single `mousedown`/`touchstart` handler on the track (nearest thumb is chosen from the pointer's position, whether that's the first pixel of a drag or a plain click) so there's no second code path left to race. Verified with a scripted fast-drag CDP test asserting the value immediately after release matches the value after the follow-up Livewire request settles (no post-release jump).

### Fixed — Price slider didn't render or drag correctly
- The dual-thumb slider shipped as two overlapping native `<input type="range">` elements with `pointer-events` CSS tricks to let each thumb "win" over the other's full-width hit area. That approach was unreliable in practice — the thumb overflowed the 4px-tall track, and there was no click-to-jump on the track since the whole input had `pointer-events: none` outside the thumb itself. ### Fixed — Checkout no longer orphans an order when payment fails to initiate
- Root cause: a cart was considered "closed" the instant *any* Order was created from it (`whereDoesntHave('order')`), regardless of whether payment ever actually started. So when `InitiatePayment` failed (e.g. an unconfigured provider, or any transient gateway error), the customer's cart silently vanished — the very next `placeOrder` attempt resolved a brand-new, empty cart and immediately failed with "Your cart is empty," while the original order sat abandoned in the database forever with no way back to it.
- New `Cart::scopeOpen()` model scope redefines "closed" correctly: a cart stays open until its order has a payment that's actually `Pending` (in flight) or `Success` — an order whose only payment attempts are `Failed`, or that has no payment at all yet, is still "the thing checkout is working on." `GetCurrentCart`, `ResolveCurrentCart`, and `CartIndicator` (which previously duplicated the same cart-resolution query inline) all now use this one shared scope instead of drifting independently.
- This makes `CreateOrderFromCart`'s existing (previously almost unreachable) idempotency guard actually fire on retry — a customer clicking "Place order" again after a failure now reuses the *same* order (no duplicate row, no re-reserved stock) and simply attempts payment again via `InitiatePayment`, which already starts a fresh attempt whenever the last one was `Failed`. Retry is just "click the same button again," with no new page or component needed.
- Per `docs/AGENTS.md` §4a, row-locking (`lockForUpdate()`) is deliberately reserved for only two Actions in the system (`ReserveStockForOrder`, `ApplyCouponToOrder`) — `InitiatePayment`'s own idempotency check is intentionally not lock-protected, so the "Place order" button's existing `wire:loading.attr="disabled"` is the actual documented mitigation against a double-click firing two payment attempts, not a DB lock.
- New `tests/Feature/Cart/CartScopeOpenTest.php` (5 tests covering every open/closed combination) and a new regression test in `CheckoutPageTest` proving a failed→retry→succeeded sequence reuses one order throughout. Fixed one pre-existing test in `CartPageTest` that had encoded the old (buggy) behavior as expected.

### Fixed — Payment initiation no longer throws an uncaught exception on a misconfigured/unreachable provider

### Fixed — Product detail page: selected variant/attribute reverted on reload, and most catalog products had no way to reach a second variant at all

### Fixed — Checkout form showed the wrong validation error under nearly every field

### Changed — Payment gateway calls are now queued (bug-hunt: no external API call was ever queued)
- There were zero `Job` classes anywhere in the app — `HandlePaymentWebhook`, `VerifyPendingPayments`, and `ProcessRefund` all called the payment gateway's `verify()`/`refund()` directly in the request/console cycle, with no `$tries`/`$timeout`/`$backoff`/`failed()` safety net, violating this project's own "external API calls must be queued" rule. Worst case: a slow/flaky provider blocked the webhook's HTTP response (risking the provider timing out and retrying) and blocked the admin "Issue refund" action.
- Added `App\Jobs\VerifyPaymentWithGateway` (used by both `HandlePaymentWebhook` and `VerifyPendingPayments` — the exact same re-check-before-and-after-the-call guard that used to live inline now lives once, in the job) and `App\Jobs\IssueProviderRefund` (used by `ProcessRefund`, dispatched only after the refund amount is already locked/reserved synchronously — the fast, contested-resource part stays synchronous; only the slow external call is deferred). Both declare `$tries = 3`, `$timeout = 30`, `$backoff = [10, 30, 60]`, and a `failed()` handler that logs the permanent failure.
- **Behavior change**: `HandlePaymentWebhook` now marks the webhook event `processed_at` immediately after dispatching the verification job, not after the gateway call resolves — receiving and queuing the event is the idempotent action; the queued job's own `payment->status !== Pending` guard is what prevents double-processing. `ProcessRefund` now returns the `Refund` while it's still `Pending` — the Filament "Issue refund" action's success notification changed from "Refund processed" to "Refund queued" accordingly, since the gateway call hasn't necessarily completed by the time the admin sees a response.
- Both new jobs, and all 4 queued Notification classes (`OrderNotification` and its subclasses, `LowStockAlert`, `ReservationsAtRiskAlert`), are now routed to named queues (`external-api`, `notifications`) instead of the undifferentiated `default` — segmentation this project's conventions require but that didn't exist anywhere in the codebase before this change. `docs/infrastructure-deployment.md` updated with the corresponding `queue:work --queue=external-api,notifications` command and a note that payment verification/refunds — not just notifications — now depend on a running queue worker.
- 5 new tests covering: the webhook dispatches (not inline-calls) verification, `VerifyPendingPayments` dispatches one job per pending payment (respecting the existing grace period), `ProcessRefund` dispatches (not inline-calls) the gateway refund and returns a `Pending` result, and both jobs' retry/timeout/queue configuration. Existing payment/refund tests continue to pass unchanged where they exercise the full flow (the test suite's `QUEUE_CONNECTION=sync` runs dispatched jobs inline), with one test updated to check the job's actual DB effect via `->fresh()` rather than the pre-dispatch in-memory object.
- Also fixed a docblock bug found in passing: `Refund.status` was typed `string` in its model docblock despite casting to the `RefundStatus` enum (same class of bug fixed for other models earlier this session) — caught by PHPStan once the new job code compared it against enum cases.

### Fixed — Third bug-hunt round: high-risk findings
- **Review soft-delete didn't free `order_item_id` for reuse**: unlike Product/ProductVariant (already fixed), `Review.order_item_id` is a foreign key, not a string, so the same "mutate to `{value}-deleted-{id}`" trick doesn't apply. `SubmitReview`'s duplicate-check correctly scopes out soft-deleted rows, so a customer deleting their review and trying to write a new one for the same purchase hit a raw unique-constraint `QueryException` instead of working. Fixed by making `order_item_id` nullable and having `DeleteReview` null it out (inside a transaction with the soft delete) — the same "free the unique value" rule, applied via nulling instead of suffixing since it's a FK. The original value remains recoverable via activity log.
- **`ClaimGuestOrder` didn't verify the claiming email was actually verified** — a real account-linking bypass. Changing a profile email nulls `email_verified_at` but doesn't block using the new address elsewhere; `ClaimGuestOrder` matched `guest_email` to the authenticated user's `email` without checking `email_verified_at`, so a logged-in attacker could change their email to a victim's address and immediately claim the victim's guest order (and its order/address history) before ever verifying it. Fixed by requiring `email_verified_at !== null` alongside the existing checks — closing the exact gap this project's own "no auto-link on an unverified identifier" rule exists to prevent.
- **Coupon `value` wasn't required for Fixed/Percentage types**: only hidden for `FreeShipping`, so an admin could save a Fixed/Percentage coupon with a blank value. Checkout would then apply it, consume a usage slot, and silently give a $0/0% discount (`$coupon->value ?? 0` in `ApplyCouponToOrder`) with no error surfaced anywhere. Added `->required()` conditional on the coupon not being `FreeShipping`.
- 6 new tests: Review order-item reuse after delete, guest-order-claim rejection for an unverified email, and Coupon value being required for Fixed/Percentage but not FreeShipping.

### Fixed — Refund race condition and missing authorization (bug hunt, high-risk findings)
- `ProcessRefund` checked the refundable balance (`payment.amount` minus already-refunded) with no row lock, then called the payment gateway and wrote the `Refund` row in a separate, later transaction — two concurrent refund requests for the same payment (an admin double-click, or a manual refund racing `HandleLatePaymentConfirmation`'s auto-refund) could both pass the cap check and both succeed, refunding more than the original payment and over-crediting stock via the paired return movement. Fixed with the same "reserve first, confirm after" shape as `ReserveStockForOrder`: the `Payment` row is now locked (`lockForUpdate()`) inside a transaction that also inserts a `Pending` `Refund` row reserving the amount against the cap *before* the external gateway call ever happens, then a second transaction updates that same row to `Success`/`Failed` once the gateway responds. Pending refunds now count against the cap alongside Success ones, closing the exact window that made the race possible.
- The "Issue refund" table action had no `->authorize()` call at all, despite `PaymentPolicy`'s own docblock explicitly stating refunds are "gated by `update`" — anyone who could merely view the Payments resource could trigger a real refund regardless of what `update()` actually allowed. Added `->authorize(fn (Payment $record) => Auth::user()?->can('update', $record) ?? false)`.
- 4 new tests: a repeated-refunds-respect-the-cumulative-cap test (same shape as this codebase's existing stock/coupon concurrency tests), a Pending-refund-blocks-a-second-refund test proving the reservation itself (not just the eventual Success/Failed status) is what closes the race, and a policy-swap test proving the refund action's authorization actually consults `PaymentPolicy::update()` rather than relying on incidental visibility.
- Found via a 3-way parallel codebase audit (enum-comparison bugs, concurrency/money/snapshot integrity, authorization/N+1) — the remaining findings (soft-deleted Product/ProductVariant not freeing their slug/SKU for reuse, N+1 on 12 relationship columns across 8 admin tables, a few lower-risk authorization gaps, `ShippingMethod` exposing its raw bigint PK) are tracked for follow-up, not yet fixed in this change.

### Fixed — Remaining bug-hunt findings (medium/low risk)

- **N+1 queries on 8 admin resource tables**: `ActivityLogResource`, `CategoryResource`, `PaymentResource`, `StockMovementResource`, `StockReservationResource`, `ReviewResource`, `OrderResource`, and `ProductResource` all display a relationship column (e.g. `category.name`, `order.order_number`) but none eager-loaded it — every row lazy-loaded its relation individually on every page render. - **`ShippingMethod` exposed its raw bigint PK** in admin edit URLs (`/admin/shipping-methods/3/edit`) — unlike every comparable resource. Added a `HasUlid`-backed `ulid` column (new migration, backfilled for any existing rows) matching the convention used by `Order`/`Payment`/`Refund`/`ProductVariant`/`Coupon`.
- 9 new tests: Product delete-routing (single + bulk + slug-reuse-after-delete), the eager-loading assertion (parameterized across all 8 resources), and the `ShippingMethod` route-key regression.

### Fixed — Attribute/term uniqueness gaps
- `Attribute.name` had no uniqueness validation at all (only `slug` did) — two attributes could both be named "Size" with different slugs. Added `->unique(ignoreRecord: true)` on the form's `name` field.

### Added — Sprint 6 (Notifications, Epic E10)
- Laravel's built-in `notifications` table (database channel), enabling both in-account notification history for customers and the Filament admin notification bell (`->databaseNotifications()` + 30s polling on the admin panel).
- `product_variants.low_stock_threshold` (nullable, falls back to a new `store_settings.low_stock_threshold`, default 5) — neither field existed anywhere before this sprint; both editable via Filament (the variant form, and the Store Settings page).
- `App\Notifications\Channels\SmsChannel` — a custom notification channel routing through the existing `SmsGateway` contract, never a vendor SDK, registered via `Notification::extend('sms', ...)` in `AppServiceProvider`. `User::routeNotificationForSms()` routes to `phone`.
- `App\Notifications\Support\OrderRecipient` resolves the right notifiable for an order: the registered `User` (gets the `database` channel too) or an on-demand `AnonymousNotifiable` built from whichever of `guest_email`/`guest_phone` were actually captured for a guest order.
- `App\Notifications\OrderNotification` (shared base for the four order-lifecycle notifications) selects channels per-recipient: phone present → sms, email present → mail, both → both — a Google-only customer with no phone never gets an sms attempt.
- `App\Notifications\Support\SafeNotifier` wraps every send in a try/catch, logging failures — a delivery failure (SMS provider down, bad email) must never fail the order/payment/shipment/stock Action that triggered it.
- `App\Notifications\Support\StaffRecipients` resolves staff by role while tolerating a role that hasn't been seeded yet in a given deployment (`Spatie\Permission`'s `RoleDoesNotExist` would otherwise turn a missing role into a hard failure of ordinary stock-movement recording).
- Four customer-facing notifications wired into the Actions that already existed: `OrderPlaced` (`CreateOrderFromCart`), `PaymentSucceeded` (`SettlePaymentSuccess`), `PaymentFailed` (new `MarkPaymentFailed` Action, extracted from `HandlePaymentWebhook`/`VerifyPendingPayments` to keep both failure branches identical), `OrderShipped` (`AssignShipment`). All fire only `->afterCommit()` where there's a transaction to wait for.
- Two staff-facing notifications: `LowStockAlert` to every Store Keeper — fired in real time by `RecordStockMovement` the moment a variant's stock *crosses* its threshold (not on every subsequent sale while already low, to avoid spamming), plus a new daily-scheduled `CheckLowStockLevels` sweep as a safety net for anything the real-time check might miss. `ReservationsAtRiskAlert` to every Admin/Super Admin — closes a gap noted back in the Inventory sprint, where `AdjustStockWithReservationCheck` flagged reservations `at_risk` but never actually notified anyone.
- Fixed a second instance of the "unrefreshed attribute after `firstOrCreate`" bug class (first found in Sprint 3 on `Order`): `StoreSetting::current()` now re-fetches after creating a fresh row, so `low_stock_threshold` (and any future DB-default column) reliably reflects what's actually in the database rather than an unset in-memory attribute.
- Fixed two pre-existing flaky tests unrelated to this sprint's changes: `ProductVariant::factory()->create()` defaults to a random 0–100 stock, and two `CheckoutTest` cases that reserve stock could occasionally roll 0 and fail — both now pass an explicit `stock`.
- 10 new feature tests covering all four customer notifications (including the guest on-demand routing and the email-only fallback for a phone-less customer), both staff alerts, the crossing-point de-duplication for low-stock alerts, and the daily sweep.

### Changed — notifications are now queued
- All six notification classes implement `ShouldQueue` (`QUEUE_CONNECTION=database`, already configured). Matters most for `HandlePaymentWebhook`: it's a synchronous HTTP endpoint the payment provider calls, and blocking on an SMS/email round-trip there risked the provider timing out and retrying the webhook. `SafeNotifier`'s docblock updated to reflect that it now guards dispatch-time failures (the queue push itself); real delivery failures happen later inside the queue worker, governed by the queue's own retry/`failed()` handling. Requires an actual queue worker running in production — noted as the user's responsibility to provision (e.g. via a cron-driven `schedule:run` + supervisor, or a dedicated worker process).

### Added — Sprint 7 (Reviews & Wishlist, Epic E7 + E9; Coupons/E8 confirmed already complete)
- `Review` and `WishlistItem` models/migrations. `reviews.order_item_id` is the proof-of-purchase link and is **unique** — one review per purchased line item — since nothing in the docs otherwise prevented duplicate reviews of the same purchase. `wishlist_items` is registered-users-only (no guest wishlist, BRD FR-8.1), saved at variant level (not product level, consistent with cart/order lines), unique on `(user_id, product_variant_id)`.
- `App\Enums\ReviewStatus` (pending/approved/rejected) backed enum.
- **"Verified purchase" is enforced as more than the FK existing**: `SubmitReview` additionally requires the order_item's parent order to actually be `paid`/`processing`/`shipped`/`delivered` — a `pending` or `cancelled` order's line item does not count, even though the row exists the moment the order is created. This was flagged as an interpretation gap in the BRD/technical-design (the FK alone doesn't prove a completed purchase) and resolved this way with explicit confirmation.
- Review Actions (`app/Actions/Review/`): `SubmitReview` (as above, plus the duplicate-review guard), `EditReview` (author only; always resets `status` back to `pending`, closing the loophole of quietly changing content on an already-approved review), `DeleteReview` (the author, or Admin/Super Admin as a moderation action — soft delete, preserving the row for audit), `ModerateReview` (staff only; can change only `status`, has no way to touch `rating`/`title`/`body` by construction — enforced by the Action's own signature, not just convention).
- Wishlist Actions (`app/Actions/Wishlist/`): `AddToWishlist` (idempotent — re-adding an already-wishlisted variant is a no-op via `firstOrCreate`, not a duplicate row), `RemoveFromWishlist`. Names weren't prescribed anywhere in the docs (no `app/Actions/Wishlist/` folder or Action names existed before this sprint) — chosen to match the existing `AddItemToCart`/`RemoveItemFromCart` naming convention.
- Filament: moderation-only `ReviewResource` — no create route, no content-edit route (reviews are never created or content-edited via the admin panel); the table exposes Approve/Reject actions calling `ModerateReview`, plus delete/restore/force-delete. `ReviewPolicy` scopes panel access to Admin/Super Admin (Store Keeper's role never extends to reviews) and, for reuse once a storefront exists, mirrors `EditReview`/`DeleteReview`'s own authorization rules. No Filament resource for `WishlistItem` — it's a pure customer feature with no admin-management use case in the BRD.
- Confirmed Epic E8 (Coupons) needed no further work — `Coupon`/`CouponUsage` models, `ApplyCouponToOrder` (with row-locking), and a full `CouponResource` CRUD in Filament were already built when coupons were pulled forward into Sprint 3.
- Storefront UI (product-detail review display/submission form, account wishlist page) intentionally deferred, consistent with every prior sprint's backend-first pattern and the storefront gap already on record — confirmed with the user rather than assumed, since the agile roadmap's own sprint label technically said "backend + Livewire UI."
- 15 new feature tests, including both rejection paths for verified purchase (pending order, cancelled order, wrong customer), the duplicate-review guard, the content-immutability of `ModerateReview`, and the ownership rules for `EditReview`/`DeleteReview`.
