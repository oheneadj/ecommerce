# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Root `.htaccess` forwarding requests into `public/` for hosts pointing the document root at the project root.

### Changed
- Switched the storefront font from Instrument Sans to Lexend (`vite.config.js` fonts entry, `--font-sans` in `resources/css/app.css`).
- Removed Flux UI (`livewire/flux`, `livewire/blaze`) per project standard (plain Blade + Tailwind only). Rebuilt every layout, auth view, and settings view (login, register, password reset/confirm, email verification, two-factor challenge, profile, security incl. 2FA setup + passkeys, appearance, account deletion) on a new set of reusable Blade + Alpine.js primitives: `x-button`, `x-input`, `x-checkbox`, `x-modal`/`x-modal-trigger`/`x-modal-close`, `x-dropdown`, `x-menu-item`, `x-otp-input`, `x-badge`, `x-callout`, `x-icon`, `x-toast-container`. Replaced `Flux::toast()` calls in `Profile`/`Security` Livewire components with a `dispatch('toast', ...)` browser event consumed by the new toast container.

### Removed
- Unused `layouts/app/header.blade.php` app-shell variant (dead code — only the sidebar variant was wired up).
- `resources/views/flux/` published component stub overrides.

- Scaffolded `app/Actions/{Auth,Catalog,Inventory,Cart,Checkout,Payment,Order,Review}`, `app/Queries`, `app/Payments/{Contracts,Drivers}`, `app/Sms/{Contracts,Drivers}` per `AGENTS.md`'s architecture map.
- Customer authentication (BRD Section 4.0): phone + OTP is now the primary login method, Google login is secondary, email+password remains available as an opt-in method set up from an authenticated session.
  - `users` table gained `phone`, `phone_verified_at`, `google_id` (name/email/password now nullable) — edited directly in the original day-zero migration since this is an unshared local project with no prior deployment.
  - New `otp_codes` table + `OtpCode` model (hashed codes only, never plaintext; `isUsable()` encodes the not-expired/not-consumed/under-5-attempts rule).
  - `App\Sms\Contracts\SmsGateway` interface + `SmsManager` (Laravel Manager pattern) + `MoolreSms` driver, resolved via `config/sms.php` — no Action ever calls a vendor SDK directly.
  - `RequestOtp` (rate-limited: 1/60s, 5/hour per phone) and `VerifyOtp` (auto-registers on first successful verification, locks after 5 failed attempts) Actions.
  - `App\Livewire\Auth\PhoneLogin` component + `/login/phone` page, linked from the existing email/password login page.

  - `SetPassword` and `LinkAccountIdentifier` Actions — the latter only ever invoked for an already-authenticated session (never inferred automatically from a login attempt), used when the Google callback fires for a signed-in user.
  - 20 new feature tests covering OTP happy path/rate limiting/expiry/lockout/replay, Google login/linking/repeat-login, and SetPassword/LinkAccountIdentifier (incl. rejecting a Google account already linked elsewhere).

### Fixed
- Latent "multiple root elements" bug in all four page layouts (`layouts/app/sidebar`, `layouts/auth/{simple,card,split}`): `<x-toast-container />` was a sibling of the main content `<div>` at the `<body>` level instead of nested inside it. Only surfaces when `APP_DEBUG=true` and a Livewire full-page component is used, which is why it went undetected until the phone-login page hit it — added `PagesRenderTest` (debug-mode smoke test across all guest pages) to catch this class of bug going forward.

### Added — Sprint 1 (Catalog Management, Epic E2)
- `Category`, `Brand`, `Product`, `ProductVariant`, `AttributeValue`, `ProductImage` models and migrations. Categories support nesting via self-referential `parent_id`; products carry `status` (`draft`/`active`/`archived`) and soft deletes; variants carry price (integer pesewas), stock, and their own `status`.
- `App\Concerns\HasUlid` (ULID as a secondary route-binding key, bigint `id` stays the real primary key) and `HasFormattedMoney` (`GH₵`-formatted money accessor) traits, applied to `ProductVariant`.
- Catalog Actions: `CreateProduct` (rejects a product with zero variants — BRD E2.3, wrapped in a DB transaction), `ArchiveProduct`, `DeleteProduct` / `DeleteProductVariant` (soft-delete + slug/SKU mutated to `{original}-deleted-{id}` so the original value is immediately reusable), `AttachProductImage`.
- Filament resources for `Category`, `Brand`, and `Product` (the latter with a `VariantsRelationManager` for editing variants post-creation, and a required `Repeater` on the create form so a product can never be saved without at least one variant, per BRD E2.3).
- `CategoryPolicy`, `BrandPolicy`, `ProductPolicy` (Super Admin/Admin/Store Keeper can view/create/update; delete/restore limited to Admin+; permanent delete limited to Super Admin), auto-discovered by Laravel's model↔policy naming convention.
- 7 new feature tests covering the variant-required guard, archive vs. delete semantics, repeated create→delete→recreate slug/SKU reuse, and ULID-based route binding.

### Fixed — Sprint 1 follow-up (transactional integrity)
- `DeleteProduct` and `DeleteProductVariant` now wrap their slug/SKU mutation and soft-delete in a single `DB::transaction()` — previously two separate writes, so a failure between them could leave a soft-deleted-looking row with its original slug/SKU still permanently blocking reuse. `CreateProduct` was already transactional (unchanged). `ArchiveProduct` is a single-column update and intentionally left unwrapped.
- Audited all Catalog Actions for external side effects (SMS/payment/notification/job dispatch) that a transaction rollback couldn't undo — none found.
- Added 3 rollback tests (`test_product_deletion_rolls_back_slug_mutation_on_failure`, `test_product_variant_deletion_rolls_back_sku_mutation_on_failure`, `test_failed_product_creation_rolls_back_the_product_and_its_variants`) proving no partial writes survive a mid-transaction failure.
- Recorded transaction/row-level-locking requirements for not-yet-built Inventory/Checkout/Payment Actions in `AGENTS.md` Section 4a (`ReserveStockForOrder` and `ApplyCouponToOrder` require `lockForUpdate()`; everything else in that phase needs a transaction only) so they're implemented correctly on the first pass rather than retrofitted.
- Added `docs/infrastructure-deployment.md` (database platform/durability settings, backup policy, scheduler/queue operational requirements, new-client deployment and pre-launch checklists) and a new "4g. ACID Guarantees & Where Integrity Actually Lives" section in `docs/technical-design-ecommerce.md` (lock-discipline rule for stock/coupon writes, the invariants enforced only by the Action layer, and the audit-log exemption for `payment_api_logs`/`webhook_events`/`activity_log`).

### Added — Sprint 2 (Inventory Management, Epic E3)
- `StockMovement` (immutable per-variant stock log: sale/restock/adjustment/return/damage, always attributable to a staff member or system-triggered) and `StockReservation` (temporary hold on a variant's stock during checkout) models and migrations, plus a singleton `StoreSetting` model/table (`stock_reservation_minutes`, default 15, admin-editable without a deploy).
- `stock_reservations.order_id` is a plain nullable column with no FK constraint yet — the `orders` table doesn't exist until the Checkout sprint; the constraint will be added in that sprint's migration once it does.
- `App\Enums\StockMovementType` and `StockReservationStatus` backed enums.
- Inventory Actions (`app/Actions/Inventory/`): `RecordStockMovement` (the single write path for `stock_movements`, keeps `product_variants.stock` in sync), `ReserveStockForOrder` (row-locked via `lockForUpdate()` — one of only two Actions in the system that needs locking, the other being the not-yet-built `ApplyCouponToOrder` — availability check and reservation insert happen inside the same locked transaction, 3 deadlock retries, expiry read from `store_settings.stock_reservation_minutes`), `ReleaseExpiredReservations` (scheduled every minute via `routes/console.php`), `AdjustStockWithReservationCheck` (a physical stock count always wins over the ledger — a correction that leaves active reservations uncovered still proceeds, and the oldest uncovered reservations are flagged `at_risk` for Admin review rather than blocking the correction or silently ignoring the shortfall, per BRD FR-2.2a).
- Filament: `StockMovementResource` (list + create only — the log is immutable, no edit/delete; the create form excludes the `sale` type, which is only ever recorded automatically on payment confirmation), read-only `StockReservationResource` (system-managed, no create/edit/delete anywhere), and a Super-Admin-only `ManageStoreSettings` page for editing the reservation window.
- `StockMovementPolicy`, `StockReservationPolicy`, `StoreSettingPolicy` — Super Admin/Admin/Store Keeper can all view stock data (Store Keeper's role is scoped to inventory only, per BRD); mutation is either Action-only (movements/reservations are never edited by hand once created) or Super-Admin-only (store settings).
- 11 new feature tests covering movement→cached-stock sync, reservation creation/rejection, reservation-window configurability, scheduled expiry/release, and the manual-adjustment-vs-active-reservations conflict rule (including the at-risk flagging and the case where coverage is retained). The overselling-prevention test proves the check-then-insert invariant sequentially, since the test suite's in-memory SQLite database can't exercise true cross-connection concurrency — noted in the test's docblock rather than overclaiming coverage.

### Added — Sprint 3 (Cart & Checkout, Epic E4, plus E8 Coupons pulled forward)
- `Cart`/`CartItem` (guest-or-user, never touches stock — BRD FR-3.1) and, pulled forward from the originally-planned Sprint 7 since `CreateOrderFromCart` needed it from day one: `Coupon`/`CouponUsage` (+ `coupon_product`/`coupon_category` scope pivots, empty on both = cart-wide). Also newly built this sprint since nothing in the codebase had them yet: `Address` (nullable `user_id` for guest checkout) and `Order`/`OrderItem`/`OrderStatusHistory` — the latter finally lets `stock_reservations.order_id` get its real FK constraint, deferred since the Inventory sprint.
- `orders.cart_id` is unique — a cart converts into at most one order, ever. This is what makes `CreateOrderFromCart` idempotent: a duplicate checkout submission (double-click, back-button resubmit) returns the already-created order instead of creating a second one.
- `App\Enums\OrderStatus` and `CouponType` backed enums. `order_number` (e.g. `ORD-2026-000123`) is assigned by `OrderObserver` on creation.
- `CreateOrderFromCart` (`app/Actions/Checkout/`): reads each item's *current* variant price/details at this moment, never whatever was true when it was added to the cart (BRD Principle 8) — permanently snapshotted onto `OrderItem.item_snapshot`/`unit_price` so a later product edit/archive/delete can never change how a past order displays. Reserves stock per item via `ReserveStockForOrder` and, if a coupon code is given, applies it via `ApplyCouponToOrder` — both nested inside the one outer transaction. A guest order's `user_id` is never set from a matching `guest_email` (BRD FR-3.2a) — only `ClaimGuestOrder`, in a later sprint, can attach one, and only after the customer authenticates.
- `ApplyCouponToOrder` (`app/Actions/Checkout/`): the other of only two Actions in the system requiring row-level locking (the first being `ReserveStockForOrder`) — locks the `Coupon` row, counts actual `coupon_usages` rows (never a cached counter), and enforces `usage_limit`, `usage_limit_per_user` (by `user_id` or, for guests, `guest_email`), `min_order_amount`, `expires_at`, and product/category scope, all inside one locked transaction with 3 deadlock retries.
- `ReserveStockForOrder` (Sprint 2) updated to accept a real `Order` model instead of a raw `int $orderId` — that workaround existed only because `Order` didn't exist yet; Sprint 2's own tests updated to match.
- `AddItemToCart`, `RemoveItemFromCart`, and `MergeGuestCartIntoUser` (`app/Actions/Cart/`) — the last one isn't a documented BRD requirement, added for the expected real-world behaviour when a shopper adds items before logging in: folds the guest cart's items into an existing user cart (combining quantities) or simply reassigns the guest cart to the user if they have none yet.
- `UpdateOrderStatus` (`app/Actions/Order/`): every order status change must go through this Action so `order_status_histories` never misses an entry.
- `CartTotalsQuery`, `OrderHistoryQuery` (`app/Queries/`) — read-only, no side effects.
- Filament: `OrderResource` (no create route — only `CreateOrderFromCart` creates one; edit page only updates status + a note, routed through `UpdateOrderStatus`, never a raw column update; no delete anywhere — orders are financial/audit records) and `CouponResource`. `OrderPolicy`/`CouponPolicy` are Admin/Super-Admin-only, matching Store Keeper's inventory-only role scope from the BRD.
- Fixed a latent bug (caught by tests before it shipped): `Order` rows created without explicitly passing `discount_total`/`tax_total`/`shipping_total` left those attributes unset in memory even though the DB column defaults to `0` — a later `$order->update([...])` reusing the in-memory value could write `NULL` into a `NOT NULL` column. `CreateOrderFromCart` and `OrderFactory` now set all three explicitly.
- 24 new feature tests, including the required concurrency proofs `test_concurrent_checkout_on_last_unit_prevents_overselling` (Checkout-level, on top of Sprint 2's Inventory-level version) and `test_concurrent_coupon_use_respects_usage_limit` — both sequential rather than true cross-connection concurrency, for the same in-memory-SQLite reason noted in Sprint 2.

### Added — Sprint 4 (Payment Integration, Epic E5)
- `Payment`, `Refund` models/migrations, plus the two audit-exempt tables from `technical-design-ecommerce.md` §4g: `payment_api_logs` (every outbound call to a provider) and `webhook_events` (every inbound webhook, unique on `(provider, event_id)`). Both are written and committed on their own, before any related business-transaction processing — never nested inside it, so a rollback of order/payment bookkeeping can never erase evidence that a charge was attempted or a webhook arrived.
- `App\Enums\PaymentStatus` and `RefundStatus` backed enums.
- `App\Payments\` — a `PaymentGateway` contract, `PaymentManager` (Laravel Manager pattern, mirrors `App\Sms\SmsManager` exactly), and `MoolreGateway`/`PaystackGateway` drivers, resolved via `config/payments.php`'s channel→provider mapping (`mobile_money` → Moolre, `card` → Paystack) so both providers can be active side by side. Card/payment details are never handled directly by this platform — Paystack's hosted checkout keeps card data entirely out of PCI scope; no driver logs a raw card number.
- Payment Actions (`app/Actions/Payment/`): `InitiatePayment` (idempotent per order — reuses an existing pending payment rather than duplicating), `HandlePaymentWebhook` (verifies the provider's signature before anything else; never trusts the webhook's own reported status, always re-verifies server-side via `PaymentGateway::verify()`; idempotency is layered — the unique `(provider, event_id)` index plus a `processed_at` check, so a retried delivery never double-fulfills), `ProcessRefund` (refund amount capped against the payment's amount minus whatever's already been refunded — cross-row arithmetic the database can't constrain — restores stock via a `return` `StockMovement`), `VerifyPendingPayments` (scheduled every 2 minutes, the polling fallback for a slow/missing webhook), `HandleLatePaymentConfirmation` (a payment confirming after its reservation already expired either fulfills directly if stock is still available, or auto-refunds and cancels the order if not), and `SettlePaymentSuccess` (the shared success-handling logic both the webhook handler and the poller funnel through, so whichever arrives first "wins" and neither double-processes).
- `POST /webhooks/payments/{provider}` — thin controller, all logic in `HandlePaymentWebhook`; exempted from CSRF verification (a payment provider can't obtain a token — the driver's signature check is this endpoint's actual authenticity gate).
- Filament: read-only `PaymentResource` (no create/edit — only `InitiatePayment` creates a payment, only the webhook/polling/late-confirmation Actions change its status) with an "Issue refund" table action calling `ProcessRefund`, and a read-only `RefundsRelationManager`. `PaymentPolicy`/`RefundPolicy` are Admin/Super-Admin-only, same scope as Order/Coupon.
- `PaymentManager` registered as a container singleton in `AppServiceProvider` (mirroring `SmsManager`) — required for `PaymentManager::extend()`-registered test doubles to actually be seen by Actions resolving the manager via constructor injection.
- 14 new feature tests against a `FakePaymentGateway` test double registered via the same public `PaymentManager::extend()` point a real new provider would use — covering initiation idempotency, outbound call logging, webhook signature rejection, duplicate webhook delivery, the mutual idempotency of polling vs. webhook confirmation, both branches of late payment confirmation, and the refund-amount cap (including after a prior partial refund).

### Added — Sprint 5 (Orders & Fulfillment, Epic E6)
- `ShippingMethod` and `Shipment` models/migrations — a single-location deployment ships an order as one parcel, no splitting (matches FR-2.4's single-physical-location assumption); `AssignShipment` upserts a single shipment per order rather than creating a new one on reassignment.
- `App\Enums\ShipmentStatus` backed enum.
- `GenerateOrderInvoice` (`app/Actions/Order/`): renders a PDF receipt via `barryvdh/laravel-dompdf` (already installed since Sprint 0) reading exclusively from `Order`'s own totals and each `OrderItem.item_snapshot` — never live `Product`/`ProductVariant` data, so a regenerated invoice for an old order looks identical no matter what's since happened to the catalog. Wired into `SettlePaymentSuccess` and `HandleLatePaymentConfirmation`'s fulfillment branch via `DB::afterCommit()` — file I/O has no place inside the payment-settlement transaction. Stored on the private `local` disk at `invoices/{order_number}.pdf`, path saved to `orders.invoice_path`.
- `ClaimGuestOrder` (`app/Actions/Order/`): attaches a past guest order to the now-authenticated customer's account — requires an already-authenticated session and an exact (case-insensitive) match between the order's `guest_email` and the user's own account email; never triggered automatically by an email match anywhere else in the system (BRD FR-3.2a). Rejects an order that's already attached to an account.
- `AssignShipment` (`app/Actions/Order/`): creates or updates an order's shipment (method + tracking number), marking it `dispatched`.
- Added `Order::getSubtotalFormattedAttribute()`/`getDiscountTotalFormattedAttribute()`/`getShippingTotalFormattedAttribute()`/`getTaxTotalFormattedAttribute()` and `OrderItem::getLineTotalFormattedAttribute()` — needed because `HasFormattedMoney::formattedMoney()` is `protected` and can't be called directly from a Blade view (the invoice template needed these).
- Filament: `ShippingMethodResource` (Admin/Super-Admin-only, same scope as Coupon), plus an "Assign shipment" and "Download invoice" table action on `OrderResource`.
- `ShippingMethodPolicy` added; no separate policy for `Shipment` since it isn't its own Filament resource (managed entirely through the Orders table actions).
- 7 new feature tests, including `test_invoice_rendering_does_not_read_live_product_data` (deletes the live product/variant entirely before rendering, proving the invoice view only ever reads `item_snapshot`) and coverage of both `ClaimGuestOrder` guard conditions (email mismatch, already-attached order).
