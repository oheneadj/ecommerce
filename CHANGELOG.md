# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Root `.htaccess` forwarding requests into `public/` for hosts pointing the document root at the project root.
- `phiki/phiki` — required for Filament's `CodeEntry` infolist component (used to display JSON payloads) to actually render; it's a hard dependency of that component, not previously installed.

### Fixed — Activity log before/after values were never actually shown
- The installed `spatie/laravel-activitylog` version records the before/after attribute diff in a dedicated `attribute_changes` column (`old`/`attributes` keys) — a schema change from older versions, where this lived in `properties`. `ActivityLogsTable`'s "View changes" modal was still reading from `properties`, which this version leaves empty for the automatic diff (it's reserved for extra context added via `tapActivity()`/`withProperties()`). Every "View changes" modal was silently showing nothing useful. Fixed to read `attribute_changes`. 4 new tests verifying created/updated/deleted events log the correct before/after values, and that the modal renders them correctly.

### Added — Payment detail page (Super Admin only)
- `PaymentResource` gained a `view` page — full payment details (order, provider, channel, status, amount, provider reference) plus the raw provider callback `metadata` as formatted JSON, and an "API Logs" tab listing every outbound call made for this payment with a "View payload" action showing the full request/response payload (`PaymentApiLog`, already tracked but not previously surfaced anywhere in the admin panel). Deliberately gated to Super Admin only via the page's own `canAccess()` override — narrower than `PaymentPolicy`'s Admin+Super Admin (which still governs the list), since this page surfaces raw provider payload. The "View" row action on the Payments table is hidden for anyone who isn't Super Admin. `Payment::apiLogs()` relationship added (was missing — `PaymentApiLog` already had `payment_id`, but nothing on `Payment` pointed back). 5 new tests covering the access restriction, the row action's visibility, and the API Logs tab's scoping.

### Added — Customer messaging
- Customers list search now covers name, email, and phone (all three columns are `->searchable()`, which Filament merges into the one global search box). "Send email" and "Send SMS" row actions added — grouped into the "Actions" dropdown alongside View, matching the more-than-two-actions grouping convention — plus the same two actions on the customer's own view page, and bulk "Send email"/"Send SMS" toolbar actions. A customer missing the relevant contact method has that action hidden (row/view page) or silently skipped with a reported count (bulk).
- `SendEmailToCustomer`/`SendSmsToCustomer` Actions (staff-composed subject/body or message — not a Notification, since this isn't a reaction to a business event). `CustomerMessage` Mailable added (a plain Notification-style class didn't fit; `Mail::raw()` was tried first but is a no-op under `Mail::fake()`, making it untestable, so a real Mailable is used instead). `CustomerMissingContactMethodException` added for the Action-level guard.
- The "Send email" modal is `Width::Large` with a `RichEditor` for the body (HTML, passed straight through to the Mailable — it's staff-authored via Filament's editor, not user-submitted, so no escaping/`nl2br`). Its "To" field shows the customer's email but is disabled and `dehydrated(false)`, so it's display-only and can't be edited to redirect the email elsewhere — the Action always sends to the record's own email regardless of what's submitted. The "Send SMS" modal now matches: `Width::Large` and the same disabled/display-only "To" field showing the customer's phone. Both modals' submit buttons now read "Send email"/"Send SMS" instead of Filament's generic default "Submit" label. 1 new test covering that the SMS "To" field can't redirect the message either.
- 8 new tests covering the multi-field search, hidden-when-missing-contact-method, single-record send (row + view page), and bulk send with skip-and-report.
- `intervention/image` (^4.0) — required for Laravel's first-party `Image` facade (`illuminate/image`, bundled with the framework since 13.20) to actually process images; it was previously only a suggested, not installed, dependency.

### Added — Automatic WebP conversion
- `ConvertImageToWebp` Action: converts an uploaded image to WebP on the way to disk if it isn't already (a file already saved as `.webp` is left untouched), wired into every image `FileUpload` field in the catalog — product/general images, per-variant "Add image", and the Brand logo — via `->saveUploadedFileUsing(ConvertImageToWebp::forFileUpload())`. An unsupported/undecodable file falls back to keeping the original rather than losing the upload. 5 new tests covering conversion, the already-webp short-circuit, and that it's actually wired into all three upload points.

### Changed — Dashboard stat cards
- The four dashboard stat cards (Today's Sales, Pending Orders, Low Stock Items, New Customers) now each carry a colored description with an icon and a 7-day sparkline, matching the requested card style — same metrics, same cards, restyled. `DashboardMetricsQuery::dailySalesTrend()`/`dailyOrdersTrend()`/`dailyNewCustomersTrend()` added to feed the sparklines. Low Stock Items' sparkline is a flat line at the current count, not a fabricated trend — there's no historical snapshot of that figure to chart, it's a live count. 3 new tests covering the trend methods.

### Added — Customer addresses

Seeded two addresses (Home/Office) for Yaw Boateng and one for Abena Owusu so the tab has real data to inspect. 1 new test covering that a customer's addresses list is properly scoped to them.

### Added — Order view page and Customers resource
- Orders now have a dedicated view page (`OrderResource`'s `view` route) — order details, a link to the customer (or the guest email/phone if there's no account), shipping destination, financial breakdown, and the same "Update status"/"Assign shipment"/"Download invoice" actions the table row offers. Added a "View" button to the Orders table alongside the existing grouped actions.

Customers were previously not visible anywhere in the admin panel at all.
- 7 new tests covering the view page's customer link (registered and guest), its status/shipment actions, the customer list's staff-exclusion, the Store-Keeper access denial, and viewing a customer's order history.

### Fixed — Revenue never accounted for refunds
- `DashboardMetricsQuery::todaysSales()`/`monthlyRevenue()`, `MonthlyRevenueChart`, and `topProducts()` all counted successful payments/order items only — a refund never changes `Payment::$status` (there's no `Refunded` case) or the order's own status, so a fully-refunded order still counted as full revenue and "sold" quantity forever. Revenue is now net of successful `Refund` rows issued in the same date window (a refund reduces the period it was issued in, not the period the original payment happened in — net revenue can legitimately go negative if a month's refunds exceed its payments). `topProducts()` now subtracts quantity returned via a refund (tracked through the existing `return`-type `StockMovement` rows `ProcessRefund` already creates) in the same window. `DashboardMetricsQuery::revenueForMonth()` added (arbitrary-month net revenue) and reused by both `monthlyRevenue()` and the chart, replacing the chart's own duplicate query. 3 new tests covering refund-netted daily/monthly revenue and refund-netted top products.

### Added — Bulk variant generation
- `GenerateProductVariants` Action + a "Generate variants" header action on the Variants tab: define attribute groups (e.g. `Size: L, M, XL` and `Color: White, Blue, Black`) and it creates every combination as a separate variant (9 here) in one submission, each carrying the matching `AttributeValue` rows, instead of adding them one at a time by hand. SKUs are built from a prefix (defaults to the product's slug) plus the slugged combination (e.g. `SHIRT-WHITE-XL`). A combination that already exists on the product (same attribute name/value pairs) is skipped rather than duplicated — the notification reports how many were created vs. skipped. 5 new tests covering combination generation, attribute values on the created variants, duplicate-skipping, SKU formatting, and the admin panel wiring.

### Added — Shipment delivery
- `shipments.delivered_at` (nullable timestamp). Marking an order **Delivered** (via the existing "Update status" modal) now also marks its shipment `Delivered` and stamps `delivered_at` — there was previously no way to ever reach that status; `ShipmentStatus::Delivered` was unreachable dead code. No separate admin action needed since the order's own status is the one thing staff actually update.

### Fixed — Shipment re-assignment
- `AssignShipment` reset `dispatched_at` and re-sent the `OrderShipped` "your order has shipped" notification to the customer on **every** call — including reassigning a shipping method or fixing a typo'd tracking number on an already-dispatched shipment. Now only the first dispatch (creating a new shipment, or transitioning one still `Pending`) stamps `dispatched_at`/notifies; later calls just update the shipping method/tracking number in place.
- 4 new tests: reassignment doesn't reset `dispatched_at`/resend the notification, marking an order Delivered marks its shipment Delivered, and that doing so with no shipment at all doesn't error.

### Changed — Order modals

Removed the now-redundant `OrderResource` edit page/route and `OrderForm` schema — their only purpose was this exact status-update form. 3 new tests covering the modal update, that it's not a URL-based navigation, and that the old edit route is gone.

### Fixed — Product/variant images
- Marking an image primary no longer allows more than one primary image within the same scope (a product's general images, or one specific variant's images) — `ProductImageObserver::saving()` unsets `is_primary` on that scope's other images whenever one is saved as primary. Runs on every create/update regardless of entry point (the Images tab or the per-variant "Add image" action), so the invariant holds no matter how an image gets marked primary. 2 new tests covering the unset-on-create case and that marking one variant's image primary leaves a different variant's primary image untouched.
- `ImageColumn`s (`BrandsTable`'s logo, `ImagesRelationManager`'s images) rendered a broken-image icon for every existing upload. Filament's `ImageColumn` checks file existence on whichever disk it resolves — defaulting to `config('filament.default_filesystem_disk')`, which is `local` here — and silently renders nothing if the file isn't found there. Since the underlying files live on the `public` disk (per the earlier `FileUpload` disk fix), the column was checking the wrong disk entirely. Both columns now explicitly declare `->disk('public')`, matching their `FileUpload` counterparts.
- `ImagesRelationManager`'s image thumbnails rendered at their full native resolution instead of a small thumbnail. `->imageHeight('60')` was passed as a **string**; `ImageColumn::getImageHeight()` only appends the `px` unit for an **integer**, so a string value is used as-is, producing invalid CSS (`height: 60` with no unit) that the browser ignores entirely. Changed to `->imageHeight(60)` (int). `BrandsTable`'s logo column had the same underlying gap from the other direction — `->circular()` alone never constrained size, so with no width/height set at all it also rendered full-size; added `->imageSize(40)`.

### Fixed

Both now explicitly use `->disk('public')` — these are genuinely public catalog assets, so no signed-URL handling is needed, but leaving the disk to an ambiguous default meant uploaded images were silently unreachable via their public URL.

### Fixed — Sprint 1 follow-up (transactional integrity)
- `DeleteProduct` and `DeleteProductVariant` now wrap their slug/SKU mutation and soft-delete in a single `DB::transaction()` — previously two separate writes, so a failure between them could leave a soft-deleted-looking row with its original slug/SKU still permanently blocking reuse. `CreateProduct` was already transactional (unchanged). `ArchiveProduct` is a single-column update and intentionally left unwrapped.
- Audited all Catalog Actions for external side effects (SMS/payment/notification/job dispatch) that a transaction rollback couldn't undo — none found.
- Added 3 rollback tests (`test_product_deletion_rolls_back_slug_mutation_on_failure`, `test_product_variant_deletion_rolls_back_sku_mutation_on_failure`, `test_failed_product_creation_rolls_back_the_product_and_its_variants`) proving no partial writes survive a mid-transaction failure.
- Recorded transaction/row-level-locking requirements for not-yet-built Inventory/Checkout/Payment Actions in `AGENTS.md` Section 4a (`ReserveStockForOrder` and `ApplyCouponToOrder` require `lockForUpdate()`; everything else in that phase needs a transaction only) so they're implemented correctly on the first pass rather than retrofitted.

### Added — Sprint 2 (Inventory Management, Epic E3)
- `StockMovement` (immutable per-variant stock log: sale/restock/adjustment/return/damage, always attributable to a staff member or system-triggered) and `StockReservation` (temporary hold on a variant's stock during checkout) models and migrations, plus a singleton `StoreSetting` model/table (`stock_reservation_minutes`, default 15, admin-editable without a deploy).
- `stock_reservations.order_id` is a plain nullable column with no FK constraint yet — the `orders` table doesn't exist until the Checkout sprint; the constraint will be added in that sprint's migration once it does.
- `App\Enums\StockMovementType` and `StockReservationStatus` backed enums.
- Inventory Actions (`app/Actions/Inventory/`): `RecordStockMovement` (the single write path for `stock_movements`, keeps `product_variants.stock` in sync), `ReserveStockForOrder` (row-locked via `lockForUpdate()` — one of only two Actions in the system that needs locking, the other being the not-yet-built `ApplyCouponToOrder` — availability check and reservation insert happen inside the same locked transaction, 3 deadlock retries, expiry read from `store_settings.stock_reservation_minutes`), `ReleaseExpiredReservations` (scheduled every minute via `routes/console.php`), `AdjustStockWithReservationCheck` (a physical stock count always wins over the ledger — a correction that leaves active reservations uncovered still proceeds, and the oldest uncovered reservations are flagged `at_risk` for Admin review rather than blocking the correction or silently ignoring the shortfall, per BRD FR-2.2a).

- `StockMovementPolicy`, `StockReservationPolicy`, `StoreSettingPolicy` — Super Admin/Admin/Store Keeper can all view stock data (Store Keeper's role is scoped to inventory only, per BRD); mutation is either Action-only (movements/reservations are never edited by hand once created) or Super-Admin-only (store settings).
- 11 new feature tests covering movement→cached-stock sync, reservation creation/rejection, reservation-window configurability, scheduled expiry/release, and the manual-adjustment-vs-active-reservations conflict rule (including the at-risk flagging and the case where coverage is retained). The overselling-prevention test proves the check-then-insert invariant sequentially, since the test suite's in-memory SQLite database can't exercise true cross-connection concurrency — noted in the test's docblock rather than overclaiming coverage.

### Added — Sprint 3 (Cart & Checkout, Epic E4, plus E8 Coupons pulled forward)
- `Cart`/`CartItem` (guest-or-user, never touches stock — BRD FR-3.1) and, pulled forward from the originally-planned Sprint 7 since `CreateOrderFromCart` needed it from day one: `Coupon`/`CouponUsage` (+ `coupon_product`/`coupon_category` scope pivots, empty on both = cart-wide). Also newly built this sprint since nothing in the codebase had them yet: `Address` (nullable `user_id` for guest checkout) and `Order`/`OrderItem`/`OrderStatusHistory` — the latter finally lets `stock_reservations.order_id` get its real FK constraint, deferred since the Inventory sprint.
- `orders.cart_id` is unique — a cart converts into at most one order, ever. This is what makes `CreateOrderFromCart` idempotent: a duplicate checkout submission (double-click, back-button resubmit) returns the already-created order instead of creating a second one.
- `App\Enums\OrderStatus` and `CouponType` backed enums. `order_number` (e.g. `ORD-2026-000123`) is assigned by `OrderObserver` on creation.
- `CreateOrderFromCart` (`app/Actions/Checkout/`): reads each item's *current* variant price/details at this moment, never whatever was true when it was added to the cart (BRD Principle 8) — permanently snapshotted onto `OrderItem.item_snapshot`/`unit_price` so a later product edit/archive/delete can never change how a past order displays. Reserves stock per item via `ReserveStockForOrder` and, if a coupon code is given, applies it via `ApplyCouponToOrder` — both nested inside the one outer transaction. A guest order's `user_id` is never set from a matching `guest_email` (BRD FR-3.2a) — only `ClaimGuestOrder`, in a later sprint, can attach one, and only after the customer authenticates.
- `ApplyCouponToOrder` (`app/Actions/Checkout/`): the other of only two Actions in the system requiring row-level locking (the first being `ReserveStockForOrder`) — locks the `Coupon` row, counts actual `coupon_usages` rows (never a cached counter), and enforces `usage_limit`, `usage_limit_per_user` (by `user_id` or, for guests, `guest_email`), `min_order_amount`, `expires_at`, and product/category scope, all inside one locked transaction with 3 deadlock retries.
- `ReserveStockForOrder` (Sprint 2) updated to accept a real `Order` model instead of a raw `int $orderId` — that workaround existed only because `Order` didn't exist yet; Sprint 2's own tests updated to match.
- `AddItemToCart`, `RemoveItemFromCart`, and `MergeGuestCartIntoUser` (`app/Actions/Cart/`) — the last one isn't a documented BRD requirement, added for the expected real-world behaviour when a shopper adds items before logging in: folds the guest cart's items into an existing user cart (combining quantities) or simply reassigns the guest cart to the user if they have none yet.
- `UpdateOrderStatus` (`app/Actions/Order/`): every order status change must go through this Action so `order_status_histories` never misses an entry.
- `CartTotalsQuery`, `OrderHistoryQuery` (`app/Queries/`) — read-only, no side effects.
- Filament: `OrderResource` (no create route — only `CreateOrderFromCart` creates one; edit page only updates status + a note, routed through `UpdateOrderStatus`, never a raw column update; no delete anywhere — orders are financial/audit records) and `CouponResource`. `OrderPolicy`/`CouponPolicy` are Admin/Super-Admin-only, matching Store Keeper's inventory-only role scope from the BRD.
- Fixed a latent bug (caught by tests before it shipped): `Order` rows created without explicitly passing `discount_total`/`tax_total`/`shipping_total` left those attributes unset in memory even though the DB column defaults to `0` — a later `$order->update([...])` reusing the in-memory value could write `NULL` into a `NOT NULL` column. `CreateOrderFromCart` and `OrderFactory` now set all three explicitly.
- 24 new feature tests, including the required concurrency proofs `test_concurrent_checkout_on_last_unit_prevents_overselling` (Checkout-level, on top of Sprint 2's Inventory-level version) and `test_concurrent_coupon_use_respects_usage_limit` — both sequential rather than true cross-connection concurrency, for the same in-memory-SQLite reason noted in Sprint 2.

### Added — Sprint 4 (Payment Integration, Epic E5)
- `Payment`, `Refund` models/migrations, plus the two audit-exempt tables from `technical-design-ecommerce.md` §4g: `payment_api_logs` (every outbound call to a provider) and `webhook_events` (every inbound webhook, unique on `(provider, event_id)`). Both are written and committed on their own, before any related business-transaction processing — never nested inside it, so a rollback of order/payment bookkeeping can never erase evidence that a charge was attempted or a webhook arrived.
- `App\Enums\PaymentStatus` and `RefundStatus` backed enums.
- `App\Payments\` — a `PaymentGateway` contract, `PaymentManager` (Laravel Manager pattern, mirrors `App\Sms\SmsManager` exactly), and `MoolreGateway`/`PaystackGateway` drivers, resolved via `config/payments.php`'s channel→provider mapping (`mobile_money` → Moolre, `card` → Paystack) so both providers can be active side by side. Card/payment details are never handled directly by this platform — Paystack's hosted checkout keeps card data entirely out of PCI scope; no driver logs a raw card number.
- Payment Actions (`app/Actions/Payment/`): `InitiatePayment` (idempotent per order — reuses an existing pending payment rather than duplicating), `HandlePaymentWebhook` (verifies the provider's signature before anything else; never trusts the webhook's own reported status, always re-verifies server-side via `PaymentGateway::verify()`; idempotency is layered — the unique `(provider, event_id)` index plus a `processed_at` check, so a retried delivery never double-fulfills), `ProcessRefund` (refund amount capped against the payment's amount minus whatever's already been refunded — cross-row arithmetic the database can't constrain — restores stock via a `return` `StockMovement`), `VerifyPendingPayments` (scheduled every 2 minutes, the polling fallback for a slow/missing webhook), `HandleLatePaymentConfirmation` (a payment confirming after its reservation already expired either fulfills directly if stock is still available, or auto-refunds and cancels the order if not), and `SettlePaymentSuccess` (the shared success-handling logic both the webhook handler and the poller funnel through, so whichever arrives first "wins" and neither double-processes).
- `POST /webhooks/payments/{provider}` — thin controller, all logic in `HandlePaymentWebhook`; exempted from CSRF verification (a payment provider can't obtain a token — the driver's signature check is this endpoint's actual authenticity gate).
- Filament: read-only `PaymentResource` (no create/edit — only `InitiatePayment` creates a payment, only the webhook/polling/late-confirmation Actions change its status) with an "Issue refund" table action calling `ProcessRefund`, and a read-only `RefundsRelationManager`. `PaymentPolicy`/`RefundPolicy` are Admin/Super-Admin-only, same scope as Order/Coupon.
- `PaymentManager` registered as a container singleton in `AppServiceProvider` (mirroring `SmsManager`) — required for `PaymentManager::extend()`-registered test doubles to actually be seen by Actions resolving the manager via constructor injection.
- 14 new feature tests against a `FakePaymentGateway` test double registered via the same public `PaymentManager::extend()` point a real new provider would use — covering initiation idempotency, outbound call logging, webhook signature rejection, duplicate webhook delivery, the mutual idempotency of polling vs. webhook confirmation, both branches of late payment confirmation, and the refund-amount cap (including after a prior partial refund).

### Added — Sprint 5 (Orders & Fulfillment, Epic E6)
- `ShippingMethod` and `Shipment` models/migrations — a single-location deployment ships an order as one parcel, no splitting (matches FR-2.4's single-physical-location assumption); `AssignShipment` upserts a single shipment per order rather than creating a new one on reassignment.
- `App\Enums\ShipmentStatus` backed enum.
- `GenerateOrderInvoice` (`app/Actions/Order/`): renders a PDF receipt via `barryvdh/laravel-dompdf` (already installed since Sprint 0) reading exclusively from `Order`'s own totals and each `OrderItem.item_snapshot` — never live `Product`/`ProductVariant` data, so a regenerated invoice for an old order looks identical no matter what's since happened to the catalog. Wired into `SettlePaymentSuccess` and `HandleLatePaymentConfirmation`'s fulfillment branch via `DB::afterCommit()` — file I/O has no place inside the payment-settlement transaction. Stored on the private `local` disk at `invoices/{order_number}.pdf`, path saved to `orders.invoice_path`.
- `ClaimGuestOrder` (`app/Actions/Order/`): attaches a past guest order to the now-authenticated customer's account — requires an already-authenticated session and an exact (case-insensitive) match between the order's `guest_email` and the user's own account email; never triggered automatically by an email match anywhere else in the system (BRD FR-3.2a). - Added `Order::getSubtotalFormattedAttribute()`/`getDiscountTotalFormattedAttribute()`/`getShippingTotalFormattedAttribute()`/`getTaxTotalFormattedAttribute()` and `OrderItem::getLineTotalFormattedAttribute()` — needed because `HasFormattedMoney::formattedMoney()` is `protected` and can't be called directly from a Blade view (the invoice template needed these).
- Filament: `ShippingMethodResource` (Admin/Super-Admin-only, same scope as Coupon), plus an "Assign shipment" and "Download invoice" table action on `OrderResource`.
- `ShippingMethodPolicy` added; no separate policy for `Shipment` since it isn't its own Filament resource (managed entirely through the Orders table actions).
- 7 new feature tests, including `test_invoice_rendering_does_not_read_live_product_data` (deletes the live product/variant entirely before rendering, proving the invoice view only ever reads `item_snapshot`) and coverage of both `ClaimGuestOrder` guard conditions (email mismatch, already-attached order).

### Added — Sprint 6 (Notifications, Epic E10)
- Laravel's built-in `notifications` table (database channel), enabling both in-account notification history for customers and the Filament admin notification bell (`->databaseNotifications()` + 30s polling on the admin panel).
- `product_variants.low_stock_threshold` (nullable, falls back to a new `store_settings.low_stock_threshold`, default 5) — neither field existed anywhere before this sprint; both editable via Filament (the variant form, and the Store Settings page).

- `App\Notifications\OrderNotification` (shared base for the four order-lifecycle notifications) selects channels per-recipient: phone present → sms, email present → mail, both → both — a Google-only customer with no phone never gets an sms attempt.

- Fixed two pre-existing flaky tests unrelated to this sprint's changes: `ProductVariant::factory()->create()` defaults to a random 0–100 stock, and two `CheckoutTest` cases that reserve stock could occasionally roll 0 and fail — both now pass an explicit `stock`.
- 10 new feature tests covering all four customer notifications (including the guest on-demand routing and the email-only fallback for a phone-less customer), both staff alerts, the crossing-point de-duplication for low-stock alerts, and the daily sweep.

### Changed — notifications are now queued
- All six notification classes implement `ShouldQueue` (`QUEUE_CONNECTION=database`, already configured). Matters most for `HandlePaymentWebhook`: it's a synchronous HTTP endpoint the payment provider calls, and blocking on an SMS/email round-trip there risked the provider timing out and retrying the webhook. `SafeNotifier`'s docblock updated to reflect that it now guards dispatch-time failures (the queue push itself); real delivery failures happen later inside the queue worker, governed by the queue's own retry/`failed()` handling. Requires an actual queue worker running in production — noted as the user's responsibility to provision (e.g. via a cron-driven `schedule:run` + supervisor, or a dedicated worker process).

### Added — Sprint 7 (Reviews & Wishlist, Epic E7 + E9; Coupons/E8 confirmed already complete)

- 15 new feature tests, including both rejection paths for verified purchase (pending order, cancelled order, wrong customer), the duplicate-review guard, the content-immutability of `ModerateReview`, and the ownership rules for `EditReview`/`DeleteReview`.
